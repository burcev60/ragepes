## Жизненный цикл индекса: обновления, переобучение, снапшоты и «blue/green» деплой

FAISS — это библиотека высокопроизводительного поиска, а не полноценная СУБД. У него нет «транзакций» и «апдейтов» как в реляционных БД. Поэтому жизненный цикл индекса нужно спроектировать: как обновлять данные, когда переобучать IVF/IVFPQ, как делать снапшоты и безостановочные релизы. Ниже — практические паттерны и готовые фрагменты кода.

### 1) Модель изменений в FAISS: нет «update», есть *delete + add*

- **Обновление вектора** по ID выполняется как «удалить старый → добавить новый с тем же ID».
- **Удаление** помечает элемент как «deleted» (для IVF — внутри ячейки; для HNSW — снимает вершину/ссылки). Память от этого сильно не уменьшается — для «компактизации» нужен офлайн-перенабор.
- **Реконструкция** вектора (`reconstruct`): точная для Flat/IVFFlat/HNSW; приближённая для IVFPQ/OPQ.

    import numpy as np, faiss

    # Базовый индекс + IDMap
    d = 768
    base = faiss.IndexIVFFlat(faiss.IndexFlatL2(d), d, 2048, faiss.METRIC_L2)
    # ... base.train(train_vectors) ...
    index = faiss.IndexIDMap(base)

    # Добавление
    xb = np.load("data/xb.npy").astype('float32')
    ids = np.arange(xb.shape[0], dtype='int64')
    index.add_with_ids(xb, ids)

    # Обновление элементов с данными ID (delete + add)
    to_update_ids = np.array([10, 42, 99], dtype='int64')
    sel = faiss.IDSelectorBatch(to_update_ids)
    index.remove_ids(sel)                         # delete
    new_vectors = xb[to_update_ids] + 0.01        # пример
    index.add_with_ids(new_vectors, to_update_ids)  # add

### 2) Когда переобучать IVF/IVFPQ (train → add заново)

Переобучение (retrain) — это дорого, но иногда неизбежно. Типовые триггеры:

- **Сильный дрейф данных.** Новые векторы распределены иначе (другая тематика, домены, языки), и k-means центроиды стали нерепрезентативны.
- **Высокая доля удалений/апдейтов.** Много «дыр» в ячейках, падение recall при прежнем `nprobe`.
- **Дисбаланс листов.** Некоторые ячейки в IVF переполнены, другие — пусты (плохая навигация при фиксированном `nprobe`).
- **Изменение метрики/предобработки.** Перешли с L2 на косинус (нормализация + IP) — индексы нужно обучать/заливать заново на нормализованных данных.


#### Мини-пайплайн офлайн-перестройки

1. Снимите **список входных данных** (истина — не только текущий индекс!) и обучите новый IVF/IVFPQ на свежем срезе.
2. Залейте данные в новый индекс (*build*), сохраните на диск (`write_index`).
3. Прогоните офлайн-валидацию (Recall@K, латентности, распределения списков).
4. Загрузите новый индекс в память на проде параллельно старому и **переключитесь атомарно** (см. blue/green ниже).


### 3) «Blue/Green» деплой индекса (без простоя)

Идея: держим два индекса в памяти — *Blue* (рабочий) и *Green* (новый). Собираем Green офлайн, прогреваем, потом атомарно меняем ссылку в сервисе поиска. Сессии запросов этого не замечают.

    # Псевдокод сервиса (Python)
    from threading import Lock

    class FaissService:
        def __init__(self, index):
            self._idx = index
            self._lock = Lock()  # только для swap, не для search

        def search(self, xq, k):
            idx = self._idx             # read без блокировки
            return idx.search(xq, k)

        def swap_index(self, new_index):
            with self._lock:
                old = self._idx
                self._idx = new_index   # атомарная замена ссылки
                # old можно выгружать/удалять после дрейна

- **Параллельность:** поиск потокобезопасен, если индекс *не модифицируется*. Не выполняйте `add/remove` в том же объекте, из которого ищете.
- **Прогрев:** сразу после загрузки пробегитесь тестовыми запросами (прогрев CPU-кеша/страниц).
- **Атомарность файлов:** храните снапшоты с версионированием (например, по ISO-времени) и переключайте «current» символической ссылкой/rename.


### 4) Снапшоты и сериализация: как хранить индексы

- `faiss.write_index(index, "index.faiss")` — сохранит всю композицию (IDMap, OPQ, IVF, PQ-кодбуки и т.п.).
- `faiss.read_index("index.faiss")` — восстановит структуру. Для GPU-индексов перед сохранением сделайте `index = faiss.index_gpu_to_cpu(index_gpu)`.
- **Совместимость версий:** между различными сборками/версиями FAISS бинарная совместимость не гарантируется. Храните сырьё (эмбеддинги + ID) на случай полного rebuild при апгрейде.
- **Тонкие опции I/O:** при больших индексах рассмотрите mmap/readonly флаги (если доступны в вашей сборке) и хранение снапшотов на быстрых дисках (NVMe).

    faiss.write_index(index, f"indices/main_{timestamp}.faiss")
    index = faiss.read_index(f"indices/main_{timestamp}.faiss")

### 5) Буфер приёма (ingest buffer) и периодические мерджи

Для больших онлайновых потоков добавлений удобен двухуровневый контур:

1. **Hot-буфер** — быстрый, «лёгкий» индекс (например, `IndexHNSWFlat` или `IndexIVFFlat` с крупным `nlist`), куда пишутся новые векторы.
2. **Main-индекс** — основной большой IVFPQ/OPQ, который переобучается и заливается офлайн.


Сервис поиска объединяет ответы (сначала кандидаты из буфера, затем из main), а по расписанию буфер «сливают» в новый main и обнуляют.

### 6) Шардинг и репликация: масштабирование по N и QPS

- **Горизонтальный шардинг (IndexShards)** — делим базу на S-частей по ID/хэшу, строим независимые индексы на разных узлах/процессах; при поиске — параллельный запрос, затем merge top-K.
- **Репликация (IndexReplicas)** — держим несколько копий одного и того же индекса для масштабирования QPS; запрос направляется в любую реплику.

    # Пример локальной агрегации (упрощённо)
    shards = [faiss.IndexFlatL2(d) for _ in range(4)]
    # ... распределённо add() по шардам ...
    agg = faiss.IndexShards(d, threaded=True, own_fields=True)
    for sh in shards:
        agg.add_shard(sh)

    D, I = agg.search(xq, k)  # единая выдача из всех шардов

Плюсы шардинга: независимая перестройка одного шарда (blue/green на уровне шарда), гибкое масштабирование памяти. Минусы: сложнее балансировка и консистентность ID.

### 7) Эксплуатационные метрики и «сигналы деградации»

- **Качество:** офлайн *Recall@K* (эталон Flat на поднаборе) и онлайн-прокси (CTR, качество рекомендаций, удовлетворённость).
- **Латентность:** p50/p95/p99, CPU%/RAM, queue depth; раздельно по типам индексов (Flat/IVF/HNSW) и по размерам батчей.
- **Структура IVF:** распределение размеров ячеек (mean/variance), доля «deleted», доля пустых листов.
- **HNSW:** средняя степень, распределение длин путей, доля «висящих» вершин после удалений.
- **Регрессии:** рост nprobe/efSearch, нужный для прежнего recall, — сигнал к переобучению/перестройке.


### 8) Конкурентность и безопасность

- **Только чтение для поиска:** выполняйте `search` из многих потоков на *немодифицируемом* индексе.
- **Запрет смешивания операций:** не делайте `add/remove` в объекте, по которому одновременно идёт `search`. Для онлайновых апдейтов держите отдельный буфер или делайте swap.
- **Идempotентность I/O:** пишите на диск во временный путь, затем `rename` → он же atomic на современных FS.


### 9) Детерминизм и воспроизводимость

- **Сиды k-means/OPQ:** фиксируйте random seed для стабильных центроидов/кодбуков между прогонов.
- **Версионирование:** помечайте снапшоты: `model=v1.4; metric=IP; d=768; nlist=4096; m=16; nbits=8; built=2025-08-14T08:15Z`.
- **Манифест:** храните JSON с параметрами индекса рядом с файлом индекса; валидируйте при загрузке.


### 10) Быстрые рецепты по типам индексов

- **Flat:** простейший — апдейты, снапшоты; при росте N переключайтесь на IVF/HNSW.
- **IVFFlat:** удобен как «main без сжатия» или как «буфер для слияния»; следите за дисбалансом листов.
- **IVFPQ/OPQ:** основной рабочий лошадь для миллионов+; храните «сырые» эмбеддинги отдельно для доранжировки.
- **HNSW:** высокий recall и низкая латентность при достаточной RAM; планируйте периодический rebuild после серии массовых удалений.
