## Графовый индекс HNSW в FAISS: параметры, метрики, тюнинг качества и скорости

В этом шаге разбираем **HNSW** (Hierarchical Navigable Small World) — популярный графовый индекс для аппроксимационного поиска ближайших соседей. В FAISS он представлен семейством классов, базовый из которых — `IndexHNSWFlat`. В отличие от IVF, HNSW не требует этапа *train* и даёт высокую полноту (recall) при низкой задержке благодаря навигации по многоуровневому маломировому графу.

### 1) Идея HNSW в двух словах

- **Многоуровневый граф:** вершины — векторы, рёбра — приближённые «соседства». Верхние уровни разрежены и служат «маяками» для быстрого входа, нижний — самый плотный.
- **Поиск:** начинается с верхнего уровня и спускается вниз, локально улучшая точку (жадный спуск с beam-поиском). На нижнем уровне выполняется расширенный локальный поиск.
- **Баланс:** ключевые ручки управления — `M` (плотность связей), `efConstruction` (качество графа при построении), `efSearch` (качество/скорость при запросе).


### 2) Базовый API и основные параметры

- `IndexHNSWFlat(d, M)` — хранит полные векторы (как Flat), но добавляет граф HNSW поверх них.
- `index.hnsw.efConstruction` — качество построения (обычно 100–400). Выше ⇒ лучше recall, дороже построение и память.
- `index.hnsw.efSearch` — ширина поиска (обычно 16–128). Выше ⇒ лучше recall, выше задержка запроса.
- `index.add(xb)` — добавление векторов (обучение не требуется).
- `D, I = index.search(xq, k)` — запросы; как и в Flat, `D` и `I` — матрицы `(Q, k)`.

    import numpy as np, faiss

    xb = np.load("data/xb.npy").astype('float32')
    xq = np.load("data/xq.npy").astype('float32')
    d, k = xb.shape[1], 10

    # 1) создаём HNSW с M связями на вершину
    M = 32
    index = faiss.IndexHNSWFlat(d, M)   # метрика по умолчанию L2

    # 2) тюнинг качества построения и поиска
    index.hnsw.efConstruction = 200     # качество графа при add()
    index.hnsw.efSearch = 64            # качество/скорость при search()

    # 3) добавляем базу и ищем
    index.add(xb)
    D, I = index.search(xq, k)

### 3) Метрики: L2, Inner Product и косинус

Как и для Flat/IVF, HNSW поддерживает поиск по L2 и скалярному произведению (IP). Косинус реализуется через IP на L2-нормализованных векторах.

#### L2 (по умолчанию)

    index = faiss.IndexHNSWFlat(d, M)  # L2 по умолчанию
    index.add(xb)
    D, I = index.search(xq, k)          # МЕНЬШЕ — лучше

#### Inner Product (IP) и косинус

    def l2_normalize(a: np.ndarray) -> np.ndarray:
        n = np.linalg.norm(a, axis=1, keepdims=True)
        n = np.maximum(n, 1e-12)
        return (a / n).astype('float32')

    xbn, xqn = l2_normalize(xb), l2_normalize(xq)

    index_ip = faiss.IndexHNSWFlat(d, M)
    index_ip.metric_type = faiss.METRIC_INNER_PRODUCT  # переключаем метрику
    index_ip.add(xbn)
    D_ip, I_ip = index_ip.search(xqn, k)               # БОЛЬШЕ — лучше (косинус)

Замечание: метрику следует задавать до `add`. Для косинуса база и запросы должны быть нормализованы одинаково.

### 4) Как выбирать M, efConstruction и efSearch

- **M** — количество исходящих связей на нижнем уровне (типично 16–48). Больше M ⇒ плотнее граф, выше память и время построения, но легче добраться до «правильных» соседей.
- **efConstruction** — ширина буфера при построении (100–400 часто достаточно, 200 — хороший старт). Влияет только на *качество индекса*, не на онлайновую задержку.
- **efSearch** — главный регулятор «скорость ↔ recall» в продакшене. Низкие значения (16–32) — быстрые, но менее полные ответы; 64–128 — выше recall, дороже по времени.


Практика подбора: фиксируйте `M` и `efConstruction` на построении, а затем увеличивайте `efSearch` до тех пор, пока не достигнете требуемого *Recall@K* при приемлемой задержке.

### 5) Сложность, память и масштабируемость

- **Время поиска:** примерно пропорционально `efSearch` и `M`; в среднем логарифмически растёт с `N` благодаря многоуровневой структуре.
- **Память:** хранение самих векторов (`N·d·4` байт для `float32`) + граф (≈ `N·M·(4–8)` байт на ссылки и служебные структуры). HNSW обычно тяжелее IVF по памяти, но даёт очень высокий recall при малой задержке.
- **Построение:** чувствительно к `efConstruction`; параллелится, но остаётся существенно дороже простого `add` в Flat.


### 6) Сравнение с IVF/IVFPQ: когда HNSW лучше

- **Максимальный recall при низкой задержке** на средних объёмах (сотни тысяч — десятки миллионов), когда RAM позволяет хранить граф + векторы.
- **Отсутствие обучения** упрощает онбординг данных (нет *train*), проще инкрементальное добавление.
- **Недостаток:** хуже масштабируется по памяти, чем IVFPQ. Если RAM — узкое место, IVFPQ/OPQ почти всегда выгоднее.


### 7) Параметры через ParameterSpace и фабрику индексов

В FAISS удобно менять параметры по имени (без прямого доступа к полям) и собирать индексы фабричными строками.

#### ParameterSpace

    ps = faiss.ParameterSpace()
    ps.set_index_parameter(index, "efSearch", 80)     # то же, что index.hnsw.efSearch = 80
    # Для IVF вы бы устанавливали, например, "nprobe"

#### index_factory

    # "HNSW{M}" — базовый HNSW; варианты с постобработкой:
    spec = "HNSW32"           # HNSW с M=32
    index = faiss.index_factory(d, spec, faiss.METRIC_L2)

    # возможны комбинации с предтрансформациями/квантованием:
    # "PCA{D'},HNSW{M}"  — PCA перед HNSW
    # "HNSW32,SQ8"       — HNSW + scalar quantization (экономия памяти)

Через `index_factory` удобно быстро прототипировать варианты и затем зафиксировать выбранную конфигурацию.

### 8) Частые вопросы и подводные камни

- **GPU:** HNSW в FAISS обычно применяется на CPU; GPU-ускорение есть для Flat/IVF. Планируйте CPU-ресурсы и потоки.
- **Порядок добавления:** может влиять на структуру графа; для больших потоковых загрузок используйте стабильные сиды и контролируйте `efConstruction`.
- **Косинус:** не забудьте нормализовать и задать `metric_type = METRIC_INNER_PRODUCT` до `add`.
- **Память:** при больших `N` и крупных `M` граф быстро «съедает» RAM. Проведите предварительную оценку (см. формулу выше).
- **Удаления/обновления:** как и в других индексах FAISS, используйте обёртку *IDMap* и паттерн *delete+add*. Массовые переразвязки графа могут быть дорогими; планируйте переиндексацию офлайн.
