## Интеграция FAISS в приложение: фильтры, гибридный поиск, доранжировка и мульти-тенантность

Теперь соберём «боевой» слой вокруг FAISS: как связывать результаты с метаданными, накладывать фильтры, комбинировать векторный и лексический поиск (BM25/TF-IDF), делать доранжировку (re-rank) топ-кандидатов, организовывать мульти-тенантность и пагинацию. Всё — без самопроверок, только теория и рабочие паттерны с кодом.

### 1) Связка с метаданными: где хранить «тексты и поля»

- **FAISS хранит только вектора (или их коды)**. Заголовки, тексты, URL, теги и др. поля держите во внешнем хранилище (PostgreSQL, SQLite/DuckDB, S3/объекты, RedisJSON).
- **Ключ = ваш внешний ID** (int64/uuid). FAISS возвращает ID, а вы батчем подтягиваете метаданные по этим ключам.
- **Консистентность**: при индексации ведите журнал операций (*upsert*/*delete* по ID), чтобы восстановиться после сбоев.


### 2) Пост-фильтрация результатов (атрибуты, теги, доступы)

Базовый FAISS не «понимает» бизнес-фильтры — их накладывают *после* поиска. Чтобы сохранить полноту (recall), ищем *с запасом* K′ > K и отбрасываем элементы, не проходящие фильтр.

    import numpy as np, faiss

    # index_id — ваш индекс с IndexIDMap (поиск возвращает ВНЕШНИЕ ID)
    K, Kp = 10, 50                         # запрашиваем с запасом
    D, I = index_id.search(xq[:1], Kp)     # пример для одного запроса
    rowD, rowI = D[0], I[0]

    # допустимые ID по фильтрам (например, tag="python" и user_has_access)
    allowed = allowed_id_set               # set[int64] из вашей БД/кеша

    # пост-фильтрация и усечение до K
    picked = [(i, d) for i, d in zip(rowI, rowD) if i in allowed][:K]
    final_ids  = [i for i, _ in picked]
    final_dists= [d for _, d in picked]

- **Как выбрать K′**: начните с 3–10×K. Если часто «не добираете» результатов — увеличивайте K′.
- **Оптимизация**: храните для популярных фильтров предвычисленные множества ID (bitset/roaring bitmap) и делайте быстрое пересечение.


### 3) Доранжировка топ-кандидатов (re-rank)

Для IVFPQ/OPQ и агрессивных параметров иногда полезно пересчитать «истинные» скоры на *сырых* эмбеддингах (или с использованием более точной модели) для топ-R кандидатов.

    # предположим, что у вас сохранена матрица исходных эмбеддингов xb_raw (float32, C-contiguous)
    R = 200  # глубина доранжировки >= Kp
    cand_ids = np.unique(rowI[:R])
    cand_vecs = xb_raw[cand_ids]           # (R, d)
    q = xq[0]                              # (d,)

    # косинус/IP: при косинусе не забудьте L2-нормализацию xb_raw и q
    scores = cand_vecs @ q                 # быстрее матрично
    top = np.argsort(scores)[::-1][:K]
    final_ids = cand_ids[top]

- **Тяжёлый re-rank**: вместо линейной алгебры используйте кросс-энкодер/LLM для 20–100 документов — дорого, но точно.
- **Стабильность**: фиксируйте размер R и измеряйте прирост nDCG/Recall@K.


### 4) Гибридный поиск: векторный + лексический (BM25/keyword)

Много задач выигрывают от гибрида: объединяете кандидатов из FAISS и из BM25, нормируете скоры и агрегируете.

    import numpy as np

    def minmax(x):
        x = np.asarray(x, dtype="float32")
        lo, hi = x.min(), x.max()
        return (x - lo) / (hi - lo + 1e-9)

    # результаты двух систем
    vec_ids, vec_scores = vec_ids_arr, vec_sim_arr    # косинус/IP → БОЛЬШЕ лучше
    bm25_ids, bm25_scores = bm_ids_arr, bm_score_arr  # BM25 → БОЛЬШЕ лучше

    # объединяем по ID
    from collections import defaultdict
    score = defaultdict(lambda: [0.0, 0.0])
    for i, s in zip(vec_ids, vec_scores):  score[i][0] = s
    for i, s in zip(bm25_ids, bm25_scores):score[i][1] = s

    # нормировка и взвешенная сумма
    alpha = 0.6  # вес векторов (подбирается офлайн)
    ids = list(score.keys())
    V = np.array([v[0] for v in score.values()])
    B = np.array([v[1] for v in score.values()])
    S = alpha * minmax(V) + (1 - alpha) * minmax(B)

    order = np.argsort(S)[::-1]
    final_ids = [ids[i] for i in order[:K]]

- **Альтернатива нормировке**: Z-score, ранговая нормировка (reciprocal rank fusion), логистическая калибровка.
- **Онлайн-тюнинг**: weight `alpha` выбирайте по офлайн-метрикам, затем корректируйте A/B-тестом.

### 6) Мульти-тенантность: один индекс или много?

- **Отдельный индекс на тенанта** — просто фильтровать не нужно, изоляция по данным и SLA. Минусы: накладные (память, управление, build).
- **Один общий индекс** — кодируйте tenant_id в старших битах int64-ID и фильтруйте пост-фактум. Пример: `ID = (tenant << 32) | doc_id`. Легко выделить подмножество по маске, но требуется K′ и фильтрация.
- **IndexShards** — шард на тенанта/группу тенантов, агрегатор сверху. Позволяет балансировать память/нагрузку.


### 7) Пагинация и курсоры

- **FAISS не пагинирует сам**: сделайте один поиск на достаточно большой K″ (напр. 1000) и страницами отдавайте из памяти.
- **Надёжный курсор**: храните «seed запроса + список (id, score)» в кеше (TTL), курсор = смещение/ключ кеша.
- **С фильтрами**: обязательно ищите с запасом (K′/K″), иначе страницы «опустеют» при строгих фильтрах.


### 8) Дедупликация и кластеризация похожих результатов

- **Near-duplicate**: внутри результата объединяйте элементы с косинусом > 0.995 или L2<ε — оставляйте самый «сильный» или самый новый.
- **Диверсификация**: жадно выбирайте результаты с минимальной взаимной похожестью (MMR: *Maximal Marginal Relevance*).


### 9) Безопасность и контроль доступа

- **Фильтр по ACL**: храните разрешённые ID (или bitset) на пользователя/группу, пересекайте с результатами перед возвратом.
- **PII**: не класть персональные данные в FAISS; только ID и эмбеддинги. Метаданные — в защищённой БД.


### 10) Трассировка и метрики сервиса

- **Метрики**: p50/p95/p99, пропускная способность, размеры K′/K″, доля отфильтрованных результатов, ошибки БД при lookup.
- **Логи запросов**: текст запроса, *seed* эмбеддинга, параметры индекса (nprobe/efSearch), варианты смешивания (α), версия индекса/модели.
- **Профилирование**: доли времени *search → re-rank → metadata lookup → рендер*.
