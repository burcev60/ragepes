### Шаг 2. NearestQuery: поиск + фильтры + OrderBy

**Цель.** Уверенно писать базовый запрос «найди ближайшие» к одному вектору с серверными фильтрами, пагинацией и устойчивой сортировкой.

#### 1) Контракт NearestQuery

- `vector_name` — по какому полю искать (`text_vector`, `image_vector` и т.п.).
- `vector` — L2-нормированный вектор запроса (той же размерности, что у `vector_name`).
- `k` — сколько кандидатов вернуть (до постобработки).
- `ef_search` — качество/латентность HNSW на этапе запроса.
- `filters` — серверные ACL/контент-фильтры (`org_id`, `lang`, `created_at`…).
- `fields` — список payload-полей, которые реально нужны в ответе (не тащим лишнее).
- `order_by` — вторичная сортировка при равных score, напр. `{"created_at":"desc"}`.
- `offset` / `limit` или курсор — пагинация.

    NearestQuery(
        vector_name="text_vector",
        vector=q_text,                     # np.ndarray или list[float], L2-нормированный
        k=50,
        ef_search=64,
        filters={"org_id":"acme","lang":"ru","created_at":{">=":"2025-01-01"}},
        fields=["doc_id","title","url","created_at","section"],
        order_by={"created_at":"desc"},
        offset=0, limit=10
    )

#### 2) Фильтры ACL/контента (server-side only)

Фильтры **всегда** формируются на бэкенде по токену пользователя. Типичные поля: `org_id`, `user_id` (если нужно), `lang`, `section`, `created_at`, а также `is_deleted`/`is_draft` в `must_not`.

    {
      "must": [
        {"key":"org_id",    "match":{"value":"acme"}},
        {"key":"lang",      "match":{"value":"ru"}},
        {"key":"created_at","range":{"gte":"2025-01-01T00:00:00Z"}}
      ],
      "must_not": [
        {"key":"is_deleted","match":{"value":true}}
      ]
    }

- Держите список разрешённых полей фильтрации (allowlist) — защищает от инъекций с фронта.
- Для «данных с OCR» удобно хранить флаг `has_ocr` и фильтровать по нему, когда нужно.


#### 3) Пагинация: offset/limit vs cursor

- **offset/limit** проще, но на ANN-поиске может «прыгать» из-за недетерминированных соседей при равных скорингах.
- **Курсор** (stable paging): держите последний ключ сортировки (например, `(score, created_at, point_id)`) и просите «следующую страницу после курсора».
- *Практика:* если нужна стабильность — увеличьте `k` (например, до 200), а клиенту отдавайте окна по 20 с курсором.


#### 4) Вторичная сортировка (OrderBy)

Косинусные скоры часто совпадают до 3–4 знаков. Чтобы порядок не «дергался», вводим устойчивое сравнение:

1. Сначала по `score` (desc).
2. Дальше по `created_at` (desc/asc).
3. Последний тай-брейкер — `point_id` (asc) для детерминизма.

    def stable_sort(items, order_by):
        key, direction = next(iter(order_by.items()))
        rev = (direction == "desc")
        return sorted(items, key=lambda x: (x["score"], x["payload"].get(key), x["point_id"]),
                      reverse=rev)

#### 5) ef_search и k: как выбирать

- **k**: сколько кандидатов вы реально используете дальше (fusion, MMR, packer). Старт — 50..100.
- **ef_search**: баланс Recall@K/латентность. Старт: текст 64, image 32. Тюнинг — по валид-набору и p95.
- *Лайфхак:* поднимайте `ef_search` точечно на канале, который является «бутылочным горлышком» качества.


#### 6) Поля payload (projection)

Возвращайте только то, что нужно UI/пакеру: `doc_id`, `title`, `url`, `section`, `created_at`. Остальное можно дотащить по клику (lazy load).

#### 7) Мини-каркас NearestQuery.run()

    from qdrant_client import QdrantClient

    def nearest_query(client: QdrantClient, coll: str, *,
                      vector_name: str, vector, k: int = 50, ef: int = 64,
                      filters=None, fields=None, order_by=None,
                      offset: int = 0, limit: int = 10):
        # 1) сырой поиск (берём побольше для стабильной пагинации)
        raw = client.search(
            collection_name=coll,
            query_vector=(vector_name, vector),
            limit=max(k, offset+limit),
            with_payload={"include": fields or []},
            params={"hnsw_ef_search": ef},
            query_filter=filters
        )
        cand = [{"point_id": str(p.id),
                 "doc_id": p.payload.get("doc_id"),
                 "score": float(p.score),
                 "payload": {f:p.payload.get(f) for f in (fields or [])}} for p in raw]

        # 2) устойчивый порядок
        if order_by:
            cand = stable_sort(cand, order_by)

        # 3) пагинация
        page = cand[offset: offset+limit]

        # 4) сбор trace
        return {
          "query":{"type":"NearestQuery","params":{
            "k":k,"ef_search":ef,"filters":filters,"fields":fields,
            "order_by":order_by,"offset":offset,"limit":limit}},
          "candidate_sets":{"nearest": cand[:k]},
          "final":[{"rank":i+1,"doc_id":c["doc_id"],"point_id":c["point_id"],
                    "score":c["score"],"payload":c["payload"]} for i,c in enumerate(page)]
        }

#### 9) Мини-практика (2–3 минуты)

1. Соберите фильтр: **org_id=acme**, **lang=ru**, **created_at ≥ 2025-01-01**, **не is_deleted**. Какие поля `fields` вернёте для UI-карточки?
2. При равных `score` вы хотите показывать более свежие записи выше. Пропишите `order_by` и объясните, какой детерминизм вы добавите как третий ключ сортировки.
3. Если p95 вырос после повышения `ef_search` с 64 до 96, но Recall@10 не изменился — что откатить/зафиксировать?


#### Чек-лист готовности

- Фильтры ACL формируются на сервере; offset/limit или курсор — выбрано и задокументировано.
- Стабильная вторичная сортировка по `(score, created_at, point_id)` реализована.
- Параметры `k` и `ef_search` подобраны под SLA и качество на валид-наборе.
- `fields` минимальны и соответствуют потребностям пакера/UI.
