## 🔹 Реализация отказов

В этом уроке мы научимся создавать RAG-систему, которая умеет честно признаваться "Не знаю", когда не уверена в ответе. Это критически важная функциональность для продакшн-систем, так как галлюцинации и неправильные ответы подрывают доверие пользователей.

### 🔸 Уровни внедрения отказов

Механику отказа можно внедрить на разных этапах RAG-цепочки:

1. **Отказ на этапе ретривера (до LLM)**

  Если ни один документ не набрал достаточной релевантности, мы не вызываем модель вовсе. Преимущества подхода:

  - Экономия токенов и времени
  - Избегаем лишних запросов к LLM заведомо впустую
  - Быстрая реакция на нерелевантные запросы

  Для реализации проверяем score документов после ретривера. Если `max(scores) < threshold` — возвращаем заранее заготовленный ответ-отказ.

2. **Отказ через промпт (на этапе LLM)**

  Инструктируем саму модель отказываться при неуверенности. В системное сообщение добавляем: `Если не уверен или информации нет в контексте, отвечай: 'Не знаю'.` Проблема такого подхода в том, что базовые LLM склонны что-то отвечать всегда. Модель может не признаться в незнании. Поэтому лучше комбинировать с проверкой на уровне ретривера.

3. #### Пост-обработка ответа (после LLM)

  После получения ответа от LLM анализируем его качество. Наример:

  - Попросить модель оценить свою уверенность (например, вернуть JSON с полем `"confidence"`), а в ответе смотреть это поле и судить по нему.
  - Использовать второй вызов LLM для проверки корректности первого ответа (**self-check)**. Это более сложный и дорогой подход, двойной вызов модели, больше затрат токенов, дольше время ожидания.

Для практических систем оптимален **первый подход** (порог на ретривере) + **инструкция в промпте**. Это дает хороший баланс надежности и эффективности.

### 🔸 Интеграция Score в метаданные

На прошлом уроке мы уже реализовывали кастомный ретривер и рассматривали, как при его разработке можно внедрить score в метаданные. Тут нам это опять понадобится, но ретривер у нас может быть простым и вызывать постоянно метод `.similarity_search_with_score()` из векторного хранилища неудобно, поэтому реализуем обёртку над ретривером, которая будет имитировать обычный ретривер, но в метаданные будет записывать `score`.

    # Шаг 1: Ретривер
    from typing import Dict, Any
    from langchain_core.retrievers import BaseRetriever

    class ScoredRetriever(BaseRetriever):
        vector_store: Any
        search_kwargs: Dict

        def _get_relevant_documents(self, query):
            docs_scores = self.vector_store.similarity_search_with_score(
                query,
                **self.search_kwargs
            )
            docs_with_scores = []
            for doc, dist in docs_scores:
                doc.metadata["score"] = 1.0 / (1.0 + float(dist))
                docs_with_scores.append(doc)

            return docs_with_scores

 

### 🔸Проверка релевантности

Для второго шага создадим функцию, которая будет проверять, достаточно ли релевантны найденные документы.

Напишем функцию, которая смотрит на добавленный в метаданные тег `score`, сравнивает его с порогом и если он выше, то добавляет документ в новый список. Если ни один документ не проходит эту проверку, то функция передаёт в словаре дальше флаг `skip` для того, чтобы не вызывать модель и заготовленный ответ, случайно выбранный из списка.

    # Шаг 2: Проверяем уверенность
    import random
  
    def check_confidence(inputs, threshold=0.55):
        refusal_phrases = ["Извините, я не нашёл надёжной информации по вашему вопросу.",
                           "Не знаю. В текущей базе знаний нет достаточного контекста.",
                           "Не могу ответить уверенно — недостаточно релевантных источников."]
        conf_docs = []
        for doc in inputs['docs']:
            score = doc.metadata.get('score', 0.0)
            if score >= threshold:
                conf_docs.append(doc)
  
        if not conf_docs:
            return {
                'skip': True,
                'answer': random.choice(refusal_phrases),
                'docs': inputs['docs'],
                'used_llm': False
            }
        inputs['docs'] = conf_docs
        return inputs
> 💡 Вместо выдачи случайного ответа, тут можно реализовать какую-то логику, но в учебном примере, для простоты обойдёмся рандомом

### 🔸Вызов LLM или пропуск шага

Завершающим шагом, необходимо реализовать логику чтения флага skip, который мы передаём после проверки релевантности документов и опираясь на него либо сразу выдать шаблонный ответ "не знаю", или вызвать LLM с уже проверено релевантным контекстом.

    # Шаг 3: Если уверены - вызываем LLM
    import os
    from dotenv import load_dotenv
    from langchain_core.prompts import ChatPromptTemplate
    from langchain_core.output_parsers import StrOutputParser
    from langchain_openai import ChatOpenAI

    load_dotenv()
    MODEL = os.getenv("OPENAI_API_MODEL", "gpt-5")
    llm = ChatOpenAI(model_name=MODEL, temperature=0)

    def llm_or_skip(inputs):
        if inputs.get('skip'):
            return inputs
  
        prompt = ChatPromptTemplate.from_messages([
            ("system",
                "Ты помощник по внутренней базе знаний. "
                "Отвечай ТОЛЬКО на основе приведенного контекста. "
                "Ссылайся на источники в тексте в квадратных скобках. "
                "Если информации нет или ты не уверен — ответь: 'Не знаю'."),
            ("user",
                "Контекст:\n{context}\n\nВопрос: {question}\n\nОтвет:")
        ])
  
        # Форматируем контекст
        context_texts = [f"Источник: {doc.metadata.get('source', 'неизвестен')}\n{doc.page_content}" for doc in inputs['docs']]
        context = "\n\n---\n\n".join(context_texts)
  
        # Вызываем LLM
        llm_input = {'context': context,
                     'question': inputs['question']}
        response = (prompt | llm | StrOutputParser()).invoke(llm_input)

        return {'answer': response,
                'docs': inputs['docs']}

### 🔸Сборка цепочки и тестовый запуск

После подготовки необходимых классов и функций мы можем собрать и проверить нашу цепочку. Подготавливаем векторное хранилище и инициализируем наш кастомный ретривер, оборачиваем нужные функции в `Runnable` объекты и проверяем на ряде тестовых вопросов

    # Собираем полную цепочку
    from langchain_core.documents import Document
    from langchain_huggingface import HuggingFaceEmbeddings
    from langchain_community.vectorstores import FAISS
    from langchain_core.runnables import RunnableLambda


    docs = [
        Document(page_content="Python - язык программирования для машинного обучения", metadata={"source": "0"}),
        Document(page_content="Машинное обучение использует Python и математику", metadata={"source": "1"}),
        Document(page_content="JavaScript работает в браузере", metadata={"source": "2"}),
        Document(page_content="Deep learning - подраздел машинного обучения", metadata={"source": "3"}),
        Document(page_content="React - библиотека для JavaScript", metadata={"source": "4"}),
        Document(page_content="PyTorch - фреймворк для глубокого обучения", metadata={"source": "5"}),
        Document(page_content="Node.js - среда выполнения JavaScript", metadata={"source": "6"}),
        Document(page_content="Нейронные сети в deep learning", metadata={"source": "7"}),
    ]

    test_queries = ["Расскажи про Rust",
                    "Расскажи про JavaScript",
                    "Расскажи про машинное обучение"]

    embed_model = HuggingFaceEmbeddings(model_name="all-MiniLM-L6-v2")
    vector_store = FAISS.from_documents(docs, embed_model)
    retriever = ScoredRetriever(
        vector_store=vector_store,
        search_kwargs={"k": 5}
        )

    retriever_step = RunnableLambda(lambda q: {'question': q, 'docs': retriever.invoke(q)})
    check_step = RunnableLambda(check_confidence)
    llm_step = RunnableLambda(llm_or_skip)

    chain = retriever_step | check_step | llm_step

    for query in test_queries:
        print(f"\n{'='*60}")
        print(f"Вопрос: {query}")
        print('='*60)
  
        result = chain.invoke(query)
  
        print(f"\n💬 Ответ:\n{result['answer']}")
  
        print(f"\n📚 Источники:")
        for i, doc in enumerate(result['docs'], 1):
            source = doc.metadata.get('source', 'неизвестен')
            score = doc.metadata.get('score', 0)
            print(f"   {i}. {source} (score: {score:.3f})")

### 🔸Улучшения

Это упрощённый вариант оформления, всё разбито на отдельные функции, хотя удобнее всё это оформлять в один класс, где функции оформлены как его внутренние методы, а при инициализации в нём удобно менять разные векторные хранилища, модели, и прочие настройки.

**Например можно:**

- Подавать список ответов извне при инициализации, например подгружать из YAML файла шаблонов
- Собирать статистику в словаре, передаваемом по цепочке для вывода её в логах
- Организовать исключения, чтобы отлавливать ошибки (тоже полезно записывать в логи со статистикой)
- Иногда полезно, вместо пустого ответа, можно предусмотреть **fallback-логику (**что делать после отказа):
  - Предложить пользователю перефразировать вопрос.
  - Попробовать веб-поиск (мы как раз перейдём к этому в модуле 4 – маршрутизация запросов)
  - Логировать случай, чтобы разработчики видели, какие вопросы остаются без ответа.


Логика отказов значительно повысила **надёжность** нашего помощника. Пользователь видит, что система не всезнающая и честно сообщает о пределах своих знаний, что в долгосрочной перспективе повышает доверие к продукту
