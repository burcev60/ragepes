### Оценка мультимодального поиска — что и как мерить

**Цель.** Понять, работает ли ваш мультимодальный поиск (Text→Image, Image→Text, Image→Image), и где именно он выигрывает (OCR/Caption/Fusion/MMR).

#### 1) Разделяйте сценарии и готовьте qrels

- **Text→Image:** запросы — тексты; релевантные объекты — изображения.
- **Image→Text:** запросы — изображения; релевантные объекты — текстовые фрагменты/доки.
- (опц.) **Image→Image:** поиск похожих изображений/дедупликация.


**Разметка релевантности (qrels):** бинарная (0/1) или градуированная (0..3). Храните в простых файлах:

- `queries.csv`: *query_id,text* (для Image→Text вместо *text* храните путь к изображению/ID).
- `qrels.csv`: *query_id,doc_id,relevance* (где *doc_id* — изображение для Text→Image или текстовый док для Image→Text).
- `runs.jsonl`: по строке на запрос — ранжированный список кандидатов:

    {"query_id":"q42",
     "ranking":[{"doc_id":"d1","score":2.31},{"doc_id":"d7","score":1.88},{"doc_id":"d3","score":1.20}]}

*Агрегация:* используйте **macro-avg** (среднее по запросам). Для отчётов удобно показывать и медианы.

**Мини-пример nDCG@5 (градуированная релевантность)**

    q = "ошибка при входе"; ранжированный список и rel:
    pos: 1   2   3   4   5
    doc: d7  d3  d1  d4  d9
    rel: 3   0   2   1   0

    DCG@5 = (2^3−1)/log2(2) + (2^0−1)/log2(3) + (2^2−1)/log2(4) + (2^1−1)/log2(5) + 0
          = 7/1 + 0/1.585 + 3/2 + 1/2.322 + 0 ≈ 7 + 0 + 1.5 + 0.43 ≈ 8.93
    IDCG@5 (идеально: rel = 3,2,1,0,0) ≈ 7/1 + 3/2 + 1/1.585 ≈ 7 + 1.5 + 0.63 = 9.13
    nDCG@5 ≈ 8.93/9.13 ≈ 0.978

#### 3) Калибровка порога «не знаю»

Соберите распределения *max-score* по *нерелевантным* парам, чтобы выбрать безопасный порог:

1. Для каждого запроса возьмите максимум *fused-score* по топ-K кандидатов.
2. Разделите на валид-наборе: релевантные vs нерелевантные запросы.
3. Выберите порог, ограничивающий ложнопозитивные срабатывания (например, FPR ≤ 5%).


В проде этот порог отправляет бота в ветку *Clarify/Web/Escalate*, если уверенность низкая.

#### 4) Диагностика: где «течёт» качество

- **Text→Image ≫ Image→Text:** проверьте предобработку изображений, согласованность энкодеров, наличие *caption/OCR* каналов.
- **OCR ничего не даёт:** посмотрите conf, язык, размер шрифта; уберите шум (футеры/водяные знаки).
- **В топе дубликаты:** включите MMR/penalize-same-source после fusion.
- **Перекос по темам:** смотрите метрики по поднаборам (UI, фото, диаграммы) — возможно, нужен разный набор весов.


#### 5) Шаблон отчёта (что показать в PR/релизе)

- Таблица: Recall@1/5/10, nDCG@10, MAP — отдельно для Text→Image и Image→Text.
- Δ к базе (до/после OCR, до/после fusion, до/после MMR).
- Гистограммы max-score для калибровки порога «не знаю».
- Топ-5 win/lose кейсов (скрин с подсветкой OCR-совпадений).


#### 6) Мини-практика (2–3 минуты)

1. Дан *qrels* (Text→Image): у запроса q1 релевантны {i2:3, i5:1}. Ваш ранжированный топ-5: [i3, i2, i9, i5, i1].
 Посчитайте **Recall@5** и **nDCG@5**. Коротко интерпретируйте результат.
2. На валидации для нерелевантных запросов распределение max-score имеет 95-й перцентиль 0.41. Какой порог «не знаю» выберете, если ваша цель — FPR ≤ 5%? Что будет с Recall@1?


#### Чек-лист перед публикацией

- qrels покрывают оба направления (Text→Image и Image→Text), не только «лёгкие» запросы.
- Метрики считаются macro-avg; явно фиксирован K (например, 10).
- Порог «не знаю» выбран по валидации и задокументирован.
- В отчёте показаны Δ метрик от OCR/Caption/Fusion/MMR и разбор провалов.
