#### Использование веток и слияние

Одна из мощнейших фич Git – ветвление (branching). Допустим, у вас есть стабильная основная ветка `main`, из которой развёртывается приложение. Вы планируете добавить новую функцию. Правильно будет не коммитить сразу в main, а создать ветку `feature-X`: `git checkout -b feature-X` (создаёт ветку и переключает на неё). Теперь вы вносите изменения, делаете коммиты – они попадают в ветку feature-X. Main остаётся нетронутым, приложение стабильно.

Когда работа над функцией завершена и протестирована, нужно **слить** ветку обратно в main. Переходим на main (`git checkout main`), подгружаем свежие изменения (`git pull`), затем `git merge feature-X`. Git автоматически объединит коммиты. Если изменения в разных файлах или разных частях файла – merge пройдёт гладко. Если вы с коллегой меняли один и тот же участок кода по-разному – возникнет конфликт, Git пометит конфликтующие места, и вам вручную нужно решить, какой вариант оставить (после чего `git add` и `git commit` для завершения слияния).

После успешного merge можно удалить ветку feature-X (`git branch -d feature-X`) – её коммиты уже в main, отдельная ветка не нужна. На практике в командах часто используют **Pull Request** (или Merge Request) – это запрос на слияние: вы публикуете ветку на сервере, коллеги делают код-ревью, и по кнопке ветка вливается в основную. При этом GitHub автоматически может удалить ветку и сохранить историю обсуждений.
