#### Непрерывное развертывание

Вышеприведённый пример – это CI (тесты при коммите). Добавление CD – следующий шаг. Предположим, наш бот разворачивается в виде Docker-контейнера на сервере. Можно настроить workflow, который при публикации релиза (тег в Git) автоматически соберёт Docker-образ, отправит его в Registry (например, Docker Hub) и даже задеплоит на сервер (если, скажем, настроен доступ k8s или SSH). GitHub Actions умеет хранить секреты (пароли, ключи) в настройках репо, так что вы можете безопасно задавать credentials для деплоя.

Например, workflow для CD мог бы запускаться `on: push tags:` – т.е. когда вы создаёте git-тег v1.2.3, начинается job деплоя: сборка `docker build`, логин в Docker Hub (с использованием секретов) и `docker push`. Затем шаг деплоя: возможно, ssh на ваш сервер и запуск `docker pull` нового образа и перезапуск контейнера. Всё это может быть автоматизировано.

Таким образом, достижим сценарий: вы написали код, запушили в main – Actions протестировали (CI). Вы решили выкатить релиз – поставили тег – Actions собрали и задеплоили (CD). Многие проекты так и работают: частые автоматические деплойменты. Конечно, настройка требует усилий, но затем экономит массу времени и убирает «человеческий фактор» (скрипт не забудет прогнать тесты или собрать оптимизированную сборку, в отличие от человека).
