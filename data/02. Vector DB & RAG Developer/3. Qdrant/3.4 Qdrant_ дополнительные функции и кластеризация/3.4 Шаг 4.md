**Кластерный режим: шардинг и репликация.** 

Одно из преимуществ Qdrant – готовность к масштабированию данных. Если в коллекции миллиарды векторов, один сервер может не справиться ни по памяти, ни по нагрузке. Qdrant умеет работать кластером, распределяя коллекцию по нескольким узлам. Механизм масштабирования включает **шардинг** (разбиение данных на фрагменты) и **репликацию** (дублирование данных на нескольких узлах для отказоустойчивости). При создании коллекции можно задать параметр `shard_number` – на сколько частей разбить данные. Например, `shard_number=4` разобьёт коллекцию на 4 шарда. Если у вас 4 узла в кластере, Qdrant постарается разместить каждый шард на отдельном узле для балансировки нагрузки. Репликация задаётся параметром `replication_factor` – сколько копий каждого шарда хранить на разных узлах. Например, если `replication_factor=2` при 4 шардах, то всего будет 4*2 = 8 физических фрагментов, и каждый из 4 логических шардов хранится на двух узлах кластера. Репликация обеспечивает высокую доступность: при падении одного узла его копии на других узлах продолжают обслуживать запросы. Qdrant использует алгоритм **Raft** для координации узлов кластера и поддержания консистентности метаданных между ними. Интересная особенность: операции с отдельными векторами (запрос ближайших соседей, добавление точки) в кластерном режиме могут выполняться с приоритетом скорости и доступности – т.е. без глобальной блокировки по Raft, что повышает производительность распределённого поиска.

 

Чтобы развернуть кластер, можно запустить несколько экземпляров Qdrant и указать им друг на друга через параметры запуска (например, переменная окружения `QDRANT__CLUSTER__ENABLED="true"` и опции `--bootstrap` для присоединения узлов к первому узлу лидеру). Код приложения при работе с кластером практически не меняется – вы так же используете клиент, указывая адрес одного из узлов, а далее сервер сам распределяет запросы между нодами. Например, если коллекция шардна на 4 части, при поисковом запросе координатор сам отправит под-запросы на каждый узел/шард и объединит результаты. Для контроля консистентности при чтении можно указывать уровень согласованности (consistency level) – например, QUORUM или ALL – в запросах, чтобы ждать ответа от определённого числа реплик. По умолчанию Qdrant выполняет запрос, если ответил хотя бы один реплика-шард (level = ONE), что максимизирует скорость, но при желании можно усилить требование, чтобы читать только подтверждённые большинством реплик данные (актуально если несколько узлов могли не успеть применить последнюю запись). В целом, кластерный режим Qdrant позволяет **горизонтально масштабировать** хранение векторов и выдерживать высокую нагрузку. Вы легко можете начать с одной ноды, а затем добавить ещё, повысив `shard_number` и `replication_factor` для нужных коллекций (правда, изменение шардинга на уже заполненной коллекции требует миграции данных или создания новой коллекции с нужными параметрами и перезаписи точек).
