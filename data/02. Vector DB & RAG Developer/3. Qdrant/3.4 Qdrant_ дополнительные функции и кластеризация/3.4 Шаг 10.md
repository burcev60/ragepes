## Лабораторная 2 — «Мини-кластер Qdrant»

**Цель:** развернуть минимальный кластер Qdrant, убедиться в отказоустойчивости при репликации и выполнить ручное перераспределение шардов при добавлении узла.

### 1. Топология и подготовка

- Кластер: **3 узла** — **2 data-узла** + **1 router** (router — входная точка API).
- Создайте коллекцию с `replication_factor = 2` и рекомендуемо `shard_number ≥ 2`.


*Пример (Python, qdrant-client):*

    from qdrant_client import QdrantClient, models

    client = QdrantClient("http://localhost:6333")  # URL роутера

    client.recreate_collection(
        collection_name="articles",
        vectors_config=models.VectorParams(size=768, distance=models.Distance.COSINE),
        shard_number=2,          # ≥2, чтобы было что распределять по узлам
        replication_factor=2     # отказоустойчивость
    )

**Важно:** при *создании* коллекции Qdrant сам размещает шард(ы) и их реплики по доступным data-узлам. При *добавлении новых узлов* в self-hosted/Docker **автоматической перераскидки шардов нет** — перенос/репликацию выполняем вручную через Cluster API (см. ниже «Динамическое масштабирование»).

### 2. Базовая проверка кластера

Зафиксируйте карту шардов и реплик коллекции:

    curl http://localhost:6333/collections/articles/cluster   # карта шардов/реплик по узлам

Проверьте общее состояние коллекции и статус оптимизатора (для понимания «здоровья» перед тестами):

    curl http://localhost:6333/collections/articles

### 3. Тест на отказоустойчивость

1. **Нагрузочный прогон №1.** Выполните 10 запросов поиска к коллекции и посчитайте среднюю задержку.  
*(Можно любым удобным способом; пример — Python-скрипт с замером времени.)*
2. **Имитируйте отказ одного data-узла.** Остановите контейнер проблемного узла:

    docker stop <data_node_container>

3. **Нагрузочный прогон №2.** Повторите те же 10 запросов. Сравните среднюю задержку и долю ошибок с прогоном №1.


**Ожидаемое поведение:** при `replication_factor=2` поиск должен продолжить работать (у каждого шарда остаётся активная реплика). Латентность может вырасти из-за нагрузки на оставшийся узел. Если видите ошибки — проверьте, что у всех шардов есть хотя бы одна *Active* реплика:

    curl http://localhost:6333/collections/articles/cluster

### 4. Динамическое масштабирование (self-hosted): вручную переносим/реплицируем шарды

Добавьте **четвёртый data-узел** в кластер (docker-compose), убедитесь, что он появился в списке пиров:

    curl http://localhost:6333/cluster   # список peers с их peer_id

Посмотрите текущее распределение по коллекции:

    curl http://localhost:6333/collections/articles/cluster

**Репликация шарда на новый узел** (добавить копию шардa на 4-й peer):

    curl -X POST http://localhost:6333/collections/articles/cluster \
      -H "Content-Type: application/json" \
      -d '{
        "replicate_shard": {
          "shard_id": 0,
          "to_peer_id": <PEER_ID_4>
        }
      }'

**Перенос шарда** с узла A на узел B (полный переезд без лишних копий):

    curl -X POST http://localhost:6333/collections/articles/cluster \
      -H "Content-Type: application/json" \
      -d '{
        "move_shard": {
          "shard_id": 1,
          "from_peer_id": <PEER_ID_A>,
          "to_peer_id": <PEER_ID_4>
        }
      }'

Дождитесь, пока новые реплики станут *Active*, затем при необходимости удалите избыточные копии (drop replica) тем же Cluster API. Повторите операции для нескольких шардов до выравнивания нагрузки.

**Критерий готовности:** у каждого шарда ровно `replication_factor` активных реплик, распределённых по разным узлам; лишних копий нет.

### 5. Сравнение производительности после масштабирования

1. Снова выполните 10 поисковых запросов при той же нагрузке.
2. Сравните среднюю задержку и долю ошибок «до» и «после» добавления узла и ручного распределения шардов.


### 6. Что предоставить в ответе

- Короткое описание последовательности действий (пункты и команды).
- Скрин/вывод карты шардов `до`, `после отказа` и `после добавления 4-го узла`.
- Результаты двух нагрузочных прогонов (средняя задержка и доля ошибок): до отказа / после отказа / после масштабирования.
- Если применяли `replicate_shard`/`move_shard` — приведите примеры запросов и кратко объясните логику распределения.


*Подсказка:* чтобы упростить будущие масштабирования, изначально выбирайте `shard_number` с запасом (например, ≥2 шарда на ноду), чтобы было что равномерно раскладывать при росте кластера.

### Как запускать кластер и как именно «ронять» data-узел

**Старт кластера**

    # Запустить все сервисы в фоне
    docker compose up -d

    # Посмотреть точные имена контейнеров (понадобятся ниже)
    docker compose ps

**Проверка, что всё поднялось**

    # Состояние коллекции (через роутер)
    curl http://localhost:6333/collections/articles

    # Карта шардов и реплик
    curl http://localhost:6333/collections/articles/cluster

**Имитируем отказ одного data-узла**

Остановите *только* один контейнер data-ноды. Роутер и второй data-узел должны оставаться запущенными.

    # Пример: остановить data-узел №2 (подставьте ваш сервис/контейнер)
    docker compose stop <data-node-2>
    # или
    docker stop <имя_контейнера_data-2>

Проверьте, что роутер отвечает, а у каждого шарда осталась хотя бы одна Active-реплика:

    curl http://localhost:6333/collections/articles
    curl http://localhost:6333/collections/articles/cluster

**Запускаем бенч**

Все запросы выполняем по адресу роутера (`http://localhost:6333`):

    # Последовательно 10 запросов
    python bench_qdrant.py --host http://localhost:6333 --n 10 --concurrency 1

    # (опционально) параллельно, чтобы увидеть эффект нагрузки
    python bench_qdrant.py --host http://localhost:6333 --n 10 --concurrency 5

**Возвращаем узел в строй**

    docker compose start <data-node-2>
    # или
    docker start <имя_контейнера_data-2>

*Важно:* не используйте `docker compose down` во время эксперимента — это выключит весь стек.
Останавливайте только один data-узел, иначе поиск будет недоступен.
