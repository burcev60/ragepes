### Мониторинг и метрики: как «пощупать» Qdrant в продакшене
> После импорта данных важно следить за нагрузкой, latency и расходом памяти. Qdrant уже поставляется с встроенными метриками Prometheus — осталось включить и прочитать.

#### 5.1 Включаем HTTP-эндпоинт Prometheus

По умолчанию Docker-образ Qdrant открывает метрики на `/metrics` того же порта, что и REST-API (6333):

    # docker-compose.yml (фрагмент)
    services:
      qdrant:
        image: qdrant/qdrant:v1.9.1
        ports:
          - "6333:6333"   # REST + gRPC + /metrics

Проверь:

    curl http://localhost:6333/metrics | head

Ты увидишь набор строк Prometheus, например  
`qdrant_current_ram_bytes 2563142656`.
> ⚠️ Если разворачиваешь Qdrant из бинаря, передай флаг
> `--enable_metrics` (в новых версиях он включён по умолчанию).

#### 5.2 Что измерять в первую очередь

| Метрика Prometheus | Описание | Полезно для |
| --- | --- | --- |
| `qdrant_current_ram_bytes` | Использование RAM процессом Qdrant | контроль OOM |
| `qdrant_current_disk_bytes` | Объём данных всех сегментов | планирование диска |
| `qdrant_search_duration_seconds_bucket` | Гистограмма времени поиска | latency / SLA |
| `qdrant_update_duration_seconds_bucket` | Время операций upsert / delete | write поток |
| `qdrant_pool_hnsw_ef_current` | Текущий `ef` при поиске (динамический) | тюнинг точности |
| `qdrant_segments_count` | Сколько сегментов в коллекции | понять, пора ли optimize |

 

#### 5.3 Быстрый дашборд Grafana (шаблон)

1. Настрой Prometheus, чтобы он скрейпил `http://qdrant:6333/metrics`.

2. В Grafana создай новый Dashboard → Import → JSON:

    {
      "panels": [
        { "title": "Search p95 latency (ms)",
          "type": "stat",
          "targets": [{
            "expr": "histogram_quantile(0.95, sum(rate(qdrant_search_duration_seconds_bucket[1m])) by (le)) * 1000"
          }] },
        { "title": "RAM used (GB)",
          "type": "stat",
          "targets": [{
            "expr": "qdrant_current_ram_bytes / 1024 / 1024 / 1024"
          }] },
        { "title": "Segments per collection",
          "type": "table",
          "targets": [{
            "expr": "qdrant_segments_count"
          }] }
      ]
    }

Два-три графика уже дадут картину: если p95-latency ползёт вверх — увеличь `hnsw_ef`? Наоборот, слишком высокий RAM — понизь `ef` или включи квантование.

#### 5.4 health-check через `/collections`

Для простого мониторинга без Prometheus хватит REST-эндпоинта:

`GET /collections/{name} `

В ответе:

    {
      "points_count": 20000,
      "optimizer_status": {
        "segments_count": 3,
        "telemetry": { "ram_usage_bytes": 2.5e9 }
      }
    }

Можно раз в минуту опрашивать этот URL и слать алерт, если `ram_usage` > порога или `segments_count` резко вырос — значит накопились «мусорные» сегменты, нужен `optimize`.

#### 5.5 Советы по SLA-тонкой настройке

| Цель | Действие |
| --- | --- |
| < 50 мс на Top-10 | Увеличь `hnsw_ef` до 200–256, а `m` — ≥ 16 (цена — +RAM) |
| Экономия памяти | Включи `product_quantization` (тип SQ-8 или PQ-64) |
| Высокий write-поток | Создай коллекцию с `write_consistency: Majority` и планируй `optimize_collection` раз в час cron-job’ом |
| Быстрый рестарт | Храни данные на SSD, включи `snapshot` после крупного импорта |

 

Теперь у тебя есть минимальный tool-belt: **метрики Prometheus, REST-health-check и рецепты оптимизации**. Этого достаточно, чтобы запустить Qdrant-кластер в продакшене и уверенно реагировать на нагрузку.
