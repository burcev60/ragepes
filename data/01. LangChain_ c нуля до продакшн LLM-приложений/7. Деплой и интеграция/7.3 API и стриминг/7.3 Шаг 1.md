Теперь, когда наше приложение готово к работе в продакшене и умеет обращаться к моделям, нужно предоставить к нему удобный доступ для пользователей или других систем. Чаще всего LLM-приложения оформляют в виде **веб-сервиса с REST API**. Это позволяет отделить фронтенд (например, чат-интерфейс на сайте или в Телеграм-боте) от бекенда с LangChain-логикой. Кроме того, API можно использовать для интеграции с другими сервисами компании. В этом уроке мы создадим REST API для нашего приложения, а также реализуем **стриминг** ответов – механизм, при котором ответ отправляется клиенту по частям в режиме реального времени (как печать ответа символ за символом, как это делает ChatGPT). Стриминг значительно улучшает пользовательский опыт, сокращая воспринимаемое время ответа. Мы рассмотрим, как реализовать стрим в HTTP-сервисе с помощью FastAPI.

 

**Проектирование REST API**  
Прежде чем писать код, спланируем, какие эндпоинты понадобятся. В простейшем случае нам нужен один метод, например `POST /ask` или `POST /chat`, который будет принимать на вход вопрос пользователя (и, возможно, контекст диалога, если мы реализуем чат с памятью) и возвращать ответ. Также может быть полезен метод `GET /health` (о котором говорили ранее) для проверки работоспособности. Если ваше приложение многофункциональное, могут быть разные методы: например, `/summarize` для запроса на суммирование текста, `/analyze` для анализа и т.д. В рамках курса предположим, что у нас одна основная цепочка – ответ на вопрос, поэтому сделаем один эндпоинт.

 

При проектировании учитывайте:

- **Формат данных**: обычно REST API работает с JSON. То есть запрос `POST /ask` может содержать JSON с полями, например, `{"question": "…", "session_id": 123}` (если сессии нужны), а ответ будет `{"answer": "..."}`.

- **Метод HTTP**: GET обычно не используют для вопросов, потому что текст вопроса может быть длинным и неподходящим для URL, да и по семантике получение ответа – это скорее действие (поэтому POST подходит). GET можно использовать разве что для healthcheck или для стриминга (как упрощенный вариант, о нём ниже).

- **Авторизация**: в продакшен-API, вероятно, вы захотите ограничить доступ. Можно использовать API-ключи, токены, OAuth2 – но в нашем примере опустим это для простоты (будем считать, что API либо закрыт внутри системы, либо добавите авторизацию самостоятельно).

- **Версионирование**: имеет смысл предусмотреть версию API, например, `POST /v1/ask` – так, в будущем при изменении контрактов можно будет ввести `/v2`.
