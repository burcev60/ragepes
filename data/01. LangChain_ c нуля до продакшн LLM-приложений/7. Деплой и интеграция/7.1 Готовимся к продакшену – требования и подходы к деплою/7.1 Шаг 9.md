## «Веб-приложение: чат + RAG + инструменты + агент»

**Бизнес-цель:** собрать единый продукт «Shoply Support» с фронтом и API: чат, загрузка PDF (RAG), веб-поиск, трекинг заказа и аналитика CSV (агент). Приложение должно быть контейнеризовано, иметь документацию API и CI/CD.

### Архитектура продакшн-бота

**Компоненты (обязательно):**

- **API-backend** (например, FastAPI/аналог): эндпоинты чата, загрузки PDF, трекинга, метрик.

- **RAG-сервис**: сбор/чтение локального индекса (из М3).

- **Tools-сервис**: веб-поиск и трекинг (из М4).

- **Agent-сервис**: аналитика CSV и графики (из М5).

- **Frontend**: веб-чат, загрузка документов, просмотр графиков, бейдж источника ответа (RAG/WEB/TRACK/AGENT).

- **Хранилище**: файловая папка/том для `uploads/` (PDF, CSV), `reports/` (png/отчёты).

- **Логи и метрики**: структурированные JSON-логи + простая страница `/admin/metrics`.

**Нефункциональные требования:**

- p95 латентность ответа чата ≤ 4 сек (локально/демо).

- Безопасность данных: не логировать PII; маскировать номера заказов (последние 4 символа).

- 12-factor конфигурация (через `.env`).

### API-контракты и поведение фронта (без кода)

**Минимальные эндпоинты (должны быть описаны в OpenAPI):**

- `POST /api/ask` — чат-запрос.  
Вход: `{ "message": str }` (+ опц. `session_id`).  
Выход:

    {
      "answer": str,
      "source_type": "rag|web|track|agent",
      "citations": [
        {"type":"pdf", "source":"file.pdf", "page":2},
        {"type":"web", "url":"https://...", "published_at":"YYYY-MM-DDThh:mm:ssZ"},
        {"type":"track", "carrier":"...", "last_update":"..."},
        {"type":"plot", "path":"reports/plots/....png"}
      ],
      "latency_ms": int,
      "usage": {"prompt_tokens": int, "completion_tokens": int, "total_tokens": int}
    }

  Требование: поддержать **стриминг** (SSE/WebSocket) или синхронный режим — выберите и опишите.

- `POST /api/uploads/pdf` — загрузка PDF в RAG; возвращает количество добавленных чанков.

- `POST /api/uploads/csv` — загрузка CSV для агента; валидировать схему.

- `GET /api/orders/{id}` — трекинг заказа (проксирует tool из М4).

- `GET /healthz` — health-check (200 + `{status:"ok"}`).

- `GET /admin/metrics` — простые метрики JSON: `total_requests`, `avg_latency_ms`, `errors_by_type`, `token_cost_estimate`.

**Аутентификация и квоты:**

- Именованные роли: `admin`, `user`.

- Авторизация: API-ключ в `Authorization: Bearer ...` **или** сессии фронта — опишите выбранный вариант.

- Rate-limit: 30 req/min на ключ, 10 загрузок PDF/сутки на пользователя. При превышении — 429 + `Retry-After`.

**Фронтенд (минимум):**

- Экран **Чат**: история, индикатор стриминга, бейдж источника (RAG/WEB/TRACK/AGENT), сбоку — список цитат/ссылок; превью графиков.

- Экран **Документы**: загрузка/список PDF с размерами и датой индексации.

- Экран **Аналитика**: галерея PNG-графиков из `reports/plots/`.

- Экран **Админ** (для `admin`): метрики, последние ошибки, кнопка «очистить индекс/кэш».

**Ошибки/UX:**

- Единый формат ошибки: `{ "error": {"code": "RATE_LIMIT", "message": "…" } }`.

- Пустой ответ RAG → fallback из гайда М2, без фантазий.

- Прогресс-индикатор при загрузке и индексации.

### Сборка, деплой и CI/CD

**Контейнеризация:**

- `Dockerfile` для backend и frontend, общий `docker-compose.yml`.

- Секреты через `.env`/секрет-менеджер (укажите, где лежат `OPENAI_API_KEY`, модели, лимиты).

- Health-check контейнеров (проверка `/healthz`).

**Деплой (выберите одно и опишите):**

- Вариант A: единый VPS (reverse-proxy, TLS, systemd/Compose).

- Вариант B: PaaS (Railway/Render/аналог) — один клик/автодеплой из main.

- Вариант C: Kubernetes (минимум 1 namespace, 2 деплоймента, 1 PVC).

**CI/CD (GitHub Actions или аналог):**

- Стейджи: `test → build → scan → push → deploy`.

- Артефакты: образы с тегами `app:<git-sha>`, SBOM/scan-отчёт в `reports/`.

- Проверки перед merge: формат OpenAPI валиден; e2e-тесты проходят.

### Интеграционные и e2e-тесты + мониторинг

**Набор тестов (минимум 12):**

1. `/api/ask` с вопросом из PDF → `source_type="rag"`, есть `citations[type=pdf]`.

2. `/api/ask` «Сегодня ПВЗ открыт?» → `source_type="web"`, есть `url` и `published_at`.

3. `/api/orders/{id}` с валидным id → `status in {processing,in_transit,delivered,exception}`.

4. `/api/ask` «ТОП-5 SKU… график» → `source_type="agent"`, `citations[type=plot]` присутствует.

5. Вне базы → корректный fallback.

6. Rate-limit с 31 запросом/мин → 429 и `Retry-After`.  
7–12. Ваши сценарии (негативные и edge-cases): пустой PDF, битый CSV, таймаут поиска, 404 заказа и т.д.

**Мониторинг:**

- Считать p50/p95 латентности, error-rate, долю успешных вызовов инструментов; простая страница `/admin/metrics`.

- Логи — JSON, минимум: `ts`, `route`, `latency_ms`, `source_type`, `tool_calls`, `user_role`.

**Автоотчёт:** сформировать `reports/deploy_eval.json`:

    {
      "e2e_pass_rate": 0..100,
      "p95_latency_ms": <число>,
      "rate_limit_effectiveness": 0..100,
      "openapi_valid": true/false,
      "errors_by_type": {"RATE_LIMIT": n, "VALIDATION": n, ...}
    }

**Пороги зачёта:**

- `e2e_pass_rate ≥ 90%`, `p95_latency_ms ≤ 4000`, `openapi_valid = true`.

## Критерии оценки

- ✅ **Функциональность (40%)**: все модули связаны, UI/UX минимально удобен, API соответствует контрактам.

- ✅ **Надёжность и безопасность (25%)**: health-checks, rate-limit, корректная обработка ошибок, отсутствие PII в логах.

- ✅ **Производительность (15%)**: p95 ≤ 4 сек, метрики и логи присутствуют.

- ✅ **Инженерная культура (10%)**: OpenAPI валиден, CI/CD собирает и деплоит, образы версиируются.

- ✅ **Документация (10%)**: понятный README, переменные окружения, сценарии запуска и тестов.
