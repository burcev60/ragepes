**Пример CD пайплайна (на примере Docker Compose)**  
Для понятности, возьмём сценарий: у нас один сервер с Docker, на нём контейнер. Мы хотим, чтобы при обновлении main он перезапускался с новым кодом.

- Будем использовать GitHub Actions для деплоя. Допустим, на сервере стоит SSH-демон. Мы можем через actions просто выполнить `ssh user@server "docker pull ... && docker compose up -d"`.

- Нужно, чтобы сервер был доступен по SSH, а образ хранился в реестре.

- Workflow `deploy.yml`:

    name: Deploy
    on:
      push:
        branches: [main]
    jobs:
      deploy-prod:
        runs-on: ubuntu-latest
        if: github.ref == 'refs/heads/main'
        steps:
          - uses: actions/checkout@v3
          - name: Build Docker image
            run: |
              docker build -t myapp:${{ github.sha }} .
              echo "${{ secrets.REGISTRY_PASSWORD }}" | docker login -u "${{ secrets.REGISTRY_USER }}" --password-stdin myregistry.io
              docker tag myapp:${{ github.sha }} myregistry.io/myrepo/myapp:latest
              docker push myregistry.io/myrepo/myapp:latest
          - name: Deploy over SSH
            uses: appleboy/ssh-action@v0.1.6
            with:
              host: ${{ secrets.PROD_HOST }}
              username: ${{ secrets.PROD_USER }}
              key: ${{ secrets.SSH_KEY }}
              script: |
                docker pull myregistry.io/myrepo/myapp:latest
                docker compose -f /path/to/docker-compose.yml up -d

 

В этом примере:

- После пуша в main, собирается Docker image, пушится как `latest` в приватный реестр (авторизация через секреты).

- Затем используется готовый Action `appleboy/ssh-action` (для удобства) чтобы подключиться на сервер и выполнить команды: `docker pull` нового образа и `docker compose up -d` (который перезапустит контейнер с новым образом).

- Предполагается, что на сервере уже есть `docker-compose.yml` с описанием сервиса (например, там указано, что сервис использует образ `myregistry.io/myrepo/myapp:latest`).

- После этой команды контейнер перезапустится с новым кодом.

Конечно, это упрощённый сценарий. В реальности, у вас может быть orchestrator:  
- **Kubernetes**: CD может заключаться в применении новых manifest (kubectl apply) или обновлении образа в Deployment. Есть CD-системы (ArgoCD, Flux) которые сами следят за репозиторием с конфигами и деплоят, либо можно через CI/CD тоже.  
- **Heroku/Railway**: можно сделать deploy step, используя CLI этих платформ.  
- **Serverless**: при деплое вызвать команду обновить функцию (например, AWS lambda update).

 

Как бы то ни было, главное – свести процесс к одному скрипту, который CI/CD выполняет. Тогда у вас **каждый коммит проходит путь**: тесты -> сборка -> деплой. Если тесты не прошли – деплоя не будет (позволяет не зарелизить багованный код). Если деплой не удался – GitHub Actions пометит pipeline как failed, вы получите уведомление и сможете устранить (например, если сервер недоступен или не хватило прав и т.д.).
