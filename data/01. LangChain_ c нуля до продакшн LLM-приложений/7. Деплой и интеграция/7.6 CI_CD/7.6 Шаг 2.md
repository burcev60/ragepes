**Continuous Integration (CI) – непрерывная интеграция**  
Цель CI: автоматически проверять каждый коммит (или каждый PR) на корректность. Что входит:

- **Запуск тестов**: Юнит-тесты, интеграционные тесты. Мы уже написали некоторые. В пайплайне, как правило, поднимается чистое окружение, устанавливаются зависимости, потом запускается `pytest`. Если какой-то тест падает – сборка проваливается, разработчик видит и чинит. Например, если обновили версию LangChain и какой-то API изменился, тест упадёт – значит, надо исправить код до мерджа.

- **Статический анализ, линтинг**: Пайплайн может включать прогон линтеров (flake8, black, isort – в Python) чтобы код соответствовал стилю и не содержал подозрительных конструкций. Также можно запускать анализ безопасности (Bandit для Python – ищет уязвимости типа использования eval, или захардкоженные пароли). В CI удобно это иметь, чтобы не допустить потенциально опасный код.

- **Сборка артефактов**: Если у вас артефакт – например, Docker-образ, его можно собирать на CI. Тут встает вопрос, делать ли это на этапе CI или CD. Распространённый подход: собирать и тестировать Docker-образ на CI, а при деплое просто взять уже протестированный образ. Это избавляет от ситуации "прошли тесты на коде, но не учли что в Dockerfile что-то не то". Однако, при частых коммитах сборка образа может замедлять CI, поэтому иногда собирают образ уже на этапе CD. Решение зависит от размера и сложности сборки.

- **Пример конфигурации**: для GitHub Actions можно создать файл `.github/workflows/ci.yml`:

     

    name: CI
    on: [push, pull_request]
    jobs:
      build-test:
        runs-on: ubuntu-latest
        steps:
          - uses: actions/checkout@v3
          - uses: actions/setup-python@v4
            with:
              python-version: "3.10"
          - name: Install dependencies
            run: pip install -r requirements.txt
          - name: Run tests
            run: pytest

Это минимальный пример: при пуше или PR, он чекаутит код, ставит Python 3.10, зависимости и запускает pytest. Вы можете расширять steps, например, перед тестами запустить `flake8` или `mypy`.

 

CI поможет отловить большую часть ошибок до слияния кода. Напомню важный момент: тесты LLM часто недетерминированы. Чтобы CI не флапал (то красный, то зелёный случайно), делайте тесты устойчивыми. Либо мокируйте ответы (как показано ранее), либо ставьте `random.seed` или temperature=0 для LLM, чтобы ответы были стабильнее.
