### 🔹 Задание: Подбор параметров на мини-датасете

Практически испытаем разные настройки `chunk_size` и `overlap` на небольшом наборе данных и запросов, чтобы эмпирически определить, какие параметры дают лучшее качество ответов. Мы проведём небольшой эксперимент: возьмём мини-датасет (например, пару документов и несколько тестовых вопросов к ним), проиндексируем его при разных конфигурациях и посмотрим, насколько успешно RAG находит правильные ответы (и с каким объёмом контекста).

Автоматизированный подбор в идеале требует метрики (например, у нас есть эталонные ответы для тестовых вопросов). Если таковые есть, можно измерять точность ответов (или `precision@k`, `recall@k` – на уровне поиска). Если явных ответов нет, можно делать косвенно:

Учитывая учебный формат, достаточно продемонстрировать подход:

- Задать несколько контрольных вопросов и вручную оценить ответы при разных настройках.
- Либо, по возможности, использовать LLM-as-a-judge: спросить например: `ответ, полученный при конфигурации A, корректен ли по сравнению с источником?`.


1. Задать 2-3 варианта настроек (например: (500,50), (800,100), (1200,0) токенов).
2. Для каждого варианта построить временный индекс и ответить на набор фиксированных вопросов.
3. Сравнить, где ответы лучше (полнее, меньше галлюцинаций).
4. Отметить, сколько документов (чанков) обычно возвращалось из поиска.


 

### 🔸 **Технический подход**

- **Создание тестового набора:** Если у вас документация, придумайте 3 вопроса по ней, на которые точно есть ответы внутри. Желательно такие, чтобы ответы разной длины или находятся в разных местах.
- **Многократная индексация:** Можно сделать скрипт, который в памяти создаёт несколько индексов (например, FAISS) с разными настройками. Чтобы не перегенерировать эмбеддинги слишком много, можно заранее сгенерить embedding для каждого предложения и потом объединять по-разному. Проще, если документы небольшие, прямо построить три разных векторных индекса.
- **Автоматическая оценка:** Если есть эталонные ответы, можно проверить, входит ли эталон в сгенерированный ответ (например, на вопрос `Когда основана компания?`, эталон `1999`, проверяем, есть ли `1999` в ответе). Но лучше самостоятельно оценить содержательность.
- **Использование LLM для проверки:** Можно попросить GPT-5 сравнить ответ с исходным документом. Но это сложнее и затратнее.
- Удобнее оформить в `.ipynb` (Jupyter Notebook), чтобы сохранять вывод ячеек и писать комментарии к каждой ячейке в markdown для отчёта.
- **Логирование процесса:**
  - Какие top-k фрагменты нашлись (их метаданные).
  - Какой ответ дала модель (если вызываете модель).
  - Или, если модель не вызывается, показать содержимое фрагментов и предположить, составит ли из них ответ. Метрика *Recall@k*: нашла ли система ответ. Нужно знать эталонный текст или хотя бы "правильный документ".


 

### 🔸 Рекомендации

- **Не слишком большой тест:** 5-10 вопросов достаточно.
- **Покрытие разных сценариев:** Вопрос с коротким ответом (одно предложение) и вопрос с ответом-абзацем.
- **Учет случайности:** Лучше фиксировать `temperature=0` для LLM, чтобы он детерминированно брала факты.
- **Выбор оптимума:** Если разница минимальна, смотрим на удобство: меньше фрагментов, меньше контекста.
- **Оптимизация:** Подбор на мини-датасете даёт тренды, но не гарантирует универсальность. Например, если 300 токенов слишком мало, на больших данных тоже будет маловато.


 

### 🔸 **Пример кода (псевдо-эксперимент)**

    # импорты
    from langchain_text_splitters import RecursiveCharacterTextSplitter, TokenTextSplitter
    from langchain_community.vectorstores import FAISS
    from langchain_huggingface import HuggingFaceEmbeddings
    from langchain_core.documents import Document

    # схема конфигураций
    configs = [
        # Конфигурации для разных типов поиска
        {"name": "sparse_optimized", "chunk_size": 300, "chunk_overlap": 30, "note": "Оптимизировано для BM25"},
        {"name": "dense_optimized", "chunk_size": 800, "chunk_overlap": 100, "note": "Оптимизировано для векторного поиска"},
        {"name": "hybrid_balanced", "chunk_size": 500, "chunk_overlap": 50, "note": "Компромисс для гибридного поиска"},
    ]

    embedding_model = HuggingFaceEmbeddings(model_name="all-MiniLM-L6-v2")

    def make_splitter(cfg):
        """Возвращает сплиттер под выбранные единицы измерения."""
        if cfg["unit"] == "tokens":
    	    # encoding_name 'cl100k_base' хорошо подходит для моделей GPT-4/5
            return TokenTextSplitter(
                encoding_name="cl100k_base",
                chunk_size=cfg["chunk_size"],
                chunk_overlap=cfg["chunk_overlap"]
            )
    	# По символам — как было, но явно
        return RecursiveCharacterTextSplitter(
            chunk_size=cfg["chunk_size"],
            chunk_overlap=cfg["chunk_overlap"],
            separators=["\n\n", "\n", ". ", " ", ""],
        )

    # --- основной цикл эксперимента ---
    for cfg in configs:
        splitter = make_splitter(cfg)

            for chunk_text in splitter.split_text(doc.page_content):
                md = (doc.metadata or {}).copy() if hasattr(doc, "metadata") else {}
                chunks.append(Document(page_content=chunk_text, metadata=md))

        print(f"\nКонфигурация: {cfg['name']} "
              f"({cfg['unit']}, size={cfg['chunk_size']}, overlap={cfg['chunk_overlap']}), "
              f"всего чанков={len(chunks)}")

            docs_and_scores = db.similarity_search_with_score(q, k=k)
            print(f"Q: {q}")
            for doc, score in docs_and_scores:
                src = (doc.metadata or {}).get("source", "—")
                page = (doc.metadata or {}).get("page", "—")
                snippet = doc.page_content[:80].replace("\n", " ")
                print(f" - найден фрагмент (score={score:.4f}): {snippet}... [{src} стр.{page}]")

Скрипт перебирает конфигурации, нарезает `docs_small` на чанки и строит FAISS-индекс. Для каждого вопроса печатаются наиболее релевантные фрагменты с оценками. LLM для генерации ответа не вызывается — по найденным фрагментам видно, присутствует ли нужная информация.

**Пример вывода:**

    Конфигурация: size=500, overlap=50, всего чанков=45
    Q: В каком году основана компания?
     - найден фрагмент (score=0.12): ...компания была основана в 1999 году, сразу после... [ustav_company стр.1]
     - найден фрагмент (score=0.08): ...Основатели поставили цель изменить индустрию... [ustav_company стр.1]
    Q: Какова миссия компании?
     - найден фрагмент (score=0.15): ...Миссия компании — обеспечить клиентов... [ustav_company стр.2]
     - найден фрагмент (score=0.09): ...видение и ценности остаются неизменны... [ustav_company стр.2]
    ...
    Конфигурация: size=1200, overlap=0, всего чанков=20
    Q: В каком году основана компания?
     - найден фрагмент (score=0.20): ...компания XYZ основана в 1999 году. Основатели... [ustav_company стр.1]
     - найден фрагмент (score=0.05): ...в настоящее время компания насчитывает... [ustav_company стр.3]
    ...

Из примера видно, что обе конфигурации находят год основания (1999) уже в первом фрагменте. В режиме 500/50 попадаются два перекрывающихся кусочка (один с точным годом, второй — соседний контекст). В 1200/0 длинный фрагмент сразу покрывает всё.  
Миссия компании тоже находится в обоих случаях.  
А вот для третьего вопроса («продукт, выпущенный в 2020») можно предположить, что при 500/50 нужный текст разрезался и не попал в top-2, тогда как при 1200/0 он входит целиком.

Такой подход позволяет сравнить надёжность конфигураций и выбрать более стабильную.
