**Шаг 1: Веб-поиск как tool (SERP/кэш)**  
*Цель шага:* Дать ассистенту возможность искать информацию в интернете. Научиться использовать API веб-поиска как инструмент и понять роль кэширования результатов поиска (SERP-кэша) для эффективности.

**Объяснение:**  
Одно из самых мощных расширений возможностей LLM – подключение **веб-поиска**. С его помощью ассистент получает доступ к актуальным данным за пределами своей офлайн-базы знаний. Мы реализуем это как инструмент, назовём его, к примеру, `"Search"`. Принцип работы: модель генерирует поисковый запрос, инструмент обращается к поисковому API (например, Bing Web Search, Google через SerpAPI, Yandex XML и т.п.), получает результаты (список ссылок, сниппетов) и возвращает их модели.

**Особенности интеграции веб-поиска:**

- Формат ответа инструмента: Мы должны решить, что возвращать модели – полный HTML страниц нельзя (слишком много текста), да и модель не должна парсить HTML. Обычно возвращают или **сниппеты (фрагменты текста)**, или короткий список ссылок + описание. Например: *"1. Wiki: Python – Python is a programming language ... 2. Docs: Tutorial – ... "* и т.д. В простом варианте достаточно первых 3-5 результатов с их заголовками и коротким описанием. Этого уже часто хватает, чтобы модель нашла нужный факт.

- **Кэширование SERP:** Если модель в ходе диалога несколько раз ищет одно и то же, нет смысла платить за API каждый раз. Мы внедряем *кэш поисковых запросов*: ключ – строка запроса, значение – результаты поиска. При вызове инструмента сначала проверяем словарь (или базу) кэша; если есть – берём оттуда. Это ускоряет диалог и экономит средства (ведь API поиска обычно платный или с ограничениями). Также кэш пригодится, если модель «зациклится» на одном запросе – она будет получать тот же результат и, возможно, двигаться дальше, вместо бесконечных одинаковых поисков.

- **Ограничение по частоте:** нужно аккуратно относиться к количеству поисковых запросов. Пользователь не захочет ждать, если бот делает десятки запросов. А поисковые API могут ограничивать QPS. Поэтому иногда агентам ставят лимит: не больше N поисковых действий в одном запросе. Если модель превысила – останавливаем её с сообщением об ограничении.

Мы подготовили инструмент `WebSearchTool` (из прошлого урока в наборе). Дополняем его реализацию: используем, например, `requests` к API. Получаем JSON, извлекаем title и snippet для топ-5 результатов, формируем строку. Добавляем глобальный словарь `search_cache`: если `query` уже ключ – сразу выдаем кешированный ответ вместо HTTP-запроса.

**Пример использования:** Пользователь спрашивает: *“Какая сейчас столица самого нового независимого государства?”* Предположим, нашей локальной базы знаний нет, модель может решить: нужно поискать. Она генерирует `Action: Search, Input: "самое новое независимое государство столица"`. Инструмент делает запрос, получает результаты (вероятно, про Южный Судан, Республика Косово и т.п.), возвращает сниппет: *"South Sudan – Juba is the capital of the Republic of South Sudan, the newest sovereign state (2011)..."*. Модель получает это как Observation и может из него понять ответ: столица Джуба.
