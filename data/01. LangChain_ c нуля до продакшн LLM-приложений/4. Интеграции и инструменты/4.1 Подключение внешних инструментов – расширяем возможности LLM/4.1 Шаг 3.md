## 🔹 Обработка ошибок и ретраи инструментов

В коде примеров прошлого шага мы делали вызовы инструментов с обработкой некоторых исключений, если вы обратили внимание. Давайте уделим немного больше внимания этому важному аспекту. Обработка разных ошибок делает инструменты более надёжными, научившись обрабатывать сетевые ошибки, некорректные ответы и автоматически повторять попытки с экспоненциальной задержкой, мы избежим кучи проблем, которые часто могут возникать при эксплуатации агента. Такие, например, как:

- **Таймауты инструментов:** Каждый вызов внешнего API или длительной функции нужно ограничить по времени. Если инструмент не вернул результат, мы должны прервать вызов (например, `requests.get(..., timeout=5)`). Иначе модель будет ждать бесконечно и пользователь – тоже. Лучше вернуть ошибку ("превышено время ожидания") – модель её увидит и, возможно, попытается иначе сформулировать запрос или извинится.

- **Обработка исключений:** Внутри инструмента всегда оборачиваем код в try/except и возвращаем понятное сообщение, например `"ERROR: Weather API failed"`, `ConnectionError`, `JSONDecodeError` или любой другой тип ошибки, агент LangChain получает её и может решить, повторить запрос или извиниться и попросить попробовать позже.

- **Retry (повтор попытки):** Используем экспоненциальный backoff с джиттером для временных ошибок.

  В LangChain можно задать `ToolRetryMiddleware`, который автоматически повторяет вызовы инструментов:

    from langchain.agents.middleware importToolRetryMiddleware

        agent = create_agent(
        model=model,
        tools=[get_weather, convert_currency],
        middleware=[
            ToolRetryMiddleware(
                max_retries=3,
                backoff_factor=2.0,
                initial_delay=1.0,
                jitter=True,
                retry_on=(ConnectionError, TimeoutError),
                on_failure="return_message",
            ),
        ],
    )
  

  Если инструмент выбрасывает `ConnectionError` или `TimeoutError` по списку из `retry_on`, он будет автоматически пробовать до 3 раз (`max_retries=3`) с задержкой 1 с (`initial_delay=1.0`), 2 с и 4 с (`backoff_factor=2.0`, экспоненциальное увеличение в 2 раза) (±25% случайности `jitter`). и в итоге отработает логику `on_failure`:

  - `raise` — выбросить исключение.
  - `return_message` — вернуть текстовое сообщение с ошибкой инструменту/агенту (удобно для пользователей).

- **Circuit-breaker для инструментов:** Защищаемся от лавин ретраев. Если сервис постоянно падает (например, API недоступно), нет смысла дергать его сотню раз – это лишь тратит время. Можно реализовать простую логику: после 5 подряд неудачных вызовов блокируем дальнейшие попытки на минуту и возвращаем сообщение «Сервис недоступен». Это можно сделать в декораторе или внутри `ToolRetryMiddleware`, используя параметр `max_delay`.

- **Избежание рекурсии:** Агент порой может использовать инструмент, который сам инициирует другой вызов агента (например, инструмент вызывает агент для обработки подзадачи).Мы можем ограничивать количество итераций вызова таких подзадач. Мы уже касались этой темы в модуле RAG, когда говорили про обращение агента к ретриверу. Это как раз такой пример, найденный текст может требовать ещё контекста. Параметр `recursion_limit` как раз контролирует, сколько таких вложенных вызовов подряд разрешено, чтобы избежать бесконечной рекурсии. Если глубина вызовов превышает это значение, агент останавливается и выдаёт ошибку или отказ, вместо того чтобы зациклиться.

    result = agent.invoke(
        {"messages": [{"role": "user", "content": "Какая погода в Москве?"}]},
        {"recursion_limit": 11} # Передаём лимит
    )
  

Надёжные инструменты — ключ к стабильному поведению агента. Таймауты, обработка ошибок и повторные запросы позволяют избежать «зависаний» и делают взаимодействие с внешним миром более предсказуемым.
