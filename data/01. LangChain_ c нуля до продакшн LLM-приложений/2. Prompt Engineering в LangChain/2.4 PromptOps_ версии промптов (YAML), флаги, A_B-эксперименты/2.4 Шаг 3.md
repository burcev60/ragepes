## 🔹 A/B-эксперименты и фичефлаги

На этом шаге будем поводить A/B-тестирование разных версий промптов на пользователях, а так же посмотрим как использовать **feature flags** (фича-флаги) для управления поведением бота (в частности, переключения промптов) без перезагрузки приложения для всех пользователей.

 

### 🔸**A/B-тестирование промптов**

Методика заключается в том, что двум группам пользователей (или запросов) показываются две разные версии системы, и затем сравниваются показатели. В случае промптов, можно направить часть трафика на старый промпт (контрольная группа A), часть – на новый промпт (группа B), и собрать метрики: например, рейтинг ответов, процент решений проблем, длина диалога и т.д. Если новая версия статистически лучше – её принимаем, если хуже – откатываем. А/B тесты особенно нужны, когда изменения промпта спорные или есть сомнения, улучшит или ухудшит. Это похоже на A/B для UI или алгоритмов, только мы тестируем промпт.

 

### 🔸**Как реализовать технически**

Логика реализации проста:

1. Получили запрос
2. Рандомно (или по пользователю) выбираем, какой промпт использовать. Например, 50% запросов используют `support_answer` версии **v1**, другим **v2**.
3. В логах помечаем версию
4. Собирать фидбек (можно и без пользовательского фидбека, а по косвенным параметрам – скорость решения вопроса, количество повторных обращений и т.д.). Но иметь явную оценку качества от пользователя напрямую очень полезно
5. Анализируем результаты
> 💡 **Продолжительность теста** должна быть достаточной, чтобы набрать статистически значимое число случаев
> ⚠️ При A/B тестировании важно изолировать **только одну переменную**. То есть, когда мы тестируем промпты, все остальное (модель, логика пост-обработки и пр.) должно быть одинаковым для групп A и B. Иначе результат будет невалидным. Также желательно, чтобы группы были случайными и репрезентативными. Чаще всего делят по пользователям: один пользователь всегда попадает либо в A либо в B, чтобы опыт отдельного пользователя не был мешаниной (например, если они обратились несколько раз, а промпт разный – их может смутить непоследовательность).

 

### 🔸**Влияние на пользователей**

A/B подразумевает, что разные пользователи могут получить разный опыт. Поэтому на критичных системах нужно внимательно следить, чтобы "неудачный" вариант не нанес ущерб. Обычно такой тест запускают, будучи уверенным, что он хотя бы не хуже явно (прошёл внутренние тесты). Также, можно стартовать с небольшого процента (например, 10% на новую версию) – так лимитируется потенциальный вред.

 

### 🔸**Feature flags**

Фича-флаги – это переключатели функциональности в приложении. По сути, переменные (в конфиге, базе или сервисе feature-flag), которые определяют, какое поведение включено. Например, можно завести флаг `USE_NEW_PROMPT=True/False`. Если True – приложение берёт промпт v2, если False – v1. Это позволяет *моментально* переключаться между вариантами без изменения кода: достаточно поменять значение флага (часто эти флаги управляются через админку или специальный сервис типа LaunchDarkly, Flipper Cloud и т.п.).

Применительно к нашим промптам: вместо поля `current: v2` в YAML можно передавать версию через флаг (например, переменной окружения `PROMPT_VERSION=v2`), либо через booleans (например, `PROMPT_V2_ENABLED=True`). Флаги удобны тем, что их можно менять во время выполнения. Некоторые системы feature flags позволяют внедрять фичи постепенно, например включить новую функцию только для 10% пользователей (как A/B), или только для внутренних пользователей (по условию).

 

### 🔸**Пример использования флага**

Предположим, вы внедрили улучшенный промпт, но не уверены на 100%. Вы можете задеплоить код, но флаг `USE_NEW_PROMPT` оставить выключенным. Через панель управления (или конфиг) включить его только для себя (например по `user_id`). Вы протестируете лично в боевом окружении. Затем постепенно расширите флаг на, скажем, 20% случайных пользователей. Посмотрите метрики. Если всё хорошо – включите для 100%. Если замечены проблемы – одним переключением выключите.

 

### 🔸**В инфраструктуре**

Feature flags часто поддерживаются через SDK, т.е. у вас в коде условие не `if env_var`, а `if flag_service.is_enabled("USE_NEW_PROMPT", user_id=...)`, который может возвращать значение по заложенным правилам (например, 50/50, или user_id mod 2, или список групп). В простом случае, можно реализовать и самостоятельно (например, используя хеш от `user_id`, чтобы стабильно делить пользователей на группы).

Деление по пользователю можно делать например через `hash(user_id) mod 2` – 0 или 1, решаем какой промпт. Или если нет явного `user_id` (например, анонимный сайт), можно по сессии или куке. В крайнем случае, random при каждой сессии, но тогда один юзер за разные сессии может увидеть оба варианта – так аналитика усложняется.

С feature flags нужно учитывать, что, включая на проде новую фичу, вы должны мониторить. Хорошо, если у вас в логах видно, под каким флагом работал запрос, чтобы в случае чего быстро собрать статистику. В контексте промптов, можно логировать: `logger.info(f"Using support_answer v2 for user {id}")`.

 

### 🔸**На уровне нашего проекта**

Мы можем имитировать feature flag простым способом: например, переменная окружения `PROMPT_EXPERIMENT=1` – если 1, то используем новый YAML `current`, если 0 – старый. Или `PROMPT_VERSION=v2` – которую можно менять. Python легко читает `os.getenv`, так что это не сложно.

Для реализации A/B теста можно использовать простую функцию, вроде такой:

    import yaml
    import random
    from langchain_core.prompts import PromptTemplate

    with open("prompts.yaml", "r", encoding="utf-8") as f:
        data = yaml.safe_load(f)

    user_id = 123123
    question = "Почему мой бот не отвечает?"

    # --- Определяем, какую версию выдать (A/B) ---
    def select_version(id, a, b, b_chance=0.5):
        random.seed(id)
        ver = b if random.random() < b_chance else a
        return PromptTemplate(
            template=data["prompts"]["assistent_system"][ver],
            input_variables=["question"]
        )

    prompt_template = select_version(user_id, "v1", "v2", b_chance=0.1)

 

### 🔸**Рекомендации**

- Не запускайте A/B на совсем уж 50/50 сразу, особенно если не уверены. Начните с малого процента (canary testing).
- Следите за отзывами и метриками. Метрики стоит обдумать заранее: *что именно будет считаться "лучше"?* Это может быть что угодно: от повышения конверсии (если промпт влияет на ответы, которые продают что-то) до снижение среднего числа запросов (если промпт стал понятнее, пользователи быстрее получают свой ответ). В учебном проекте вы можете посчитать, например, среднюю длину ответа или количество последующих уточняющих вопросов – чтобы оценить, влияет ли новый промпт на стиль общения.
- Feature flags – дисциплина: не злоупотребляйте ими (иначе код превратится в кучу if-else для разных комбинаций флагов). После принятия решения по A/B обычно флаг выпиливают и оставляют только победивший вариант. Но на время эксперимента – это спасение.
- Сочетание YAML-конфигов для версий и feature flags для переключения даёт максимально гибкую систему PromptOps: вы можете запускать разные версии одновременно контролируемо и быстро мигрировать без переписывания и деплоя кода.
- Даже в небольших прототипах закладывайте эти возможности, так как LLM – вещь вероятностная, и иногда "старый проверенный промпт" – лучший запасной парашют, если новый вдруг начал генерировать ерунду.
