**Шаг 4: Артефакт – guardrails-модуль с тестами**  
**Цель шага:** Оформить результаты этого урока в виде модульного кода (например, `safety.py`), содержащего функции для валидации и безопасного запуска, и написать несколько тестов, демонстрирующих, что защитные механизмы работают.

Мы создадим файл `safety.py` где пропишем:

- `validate_code(code) -> (ok, error_msg)`

- `run_code_sandbox(code) -> (output, files)`

- Возможно, `secure_execute(code)` которая объединит: валидация -> выполнение -> результат или ошибка.

Этот модуль должны протестировать. Напишем ряд **юнит-тестов** (или просто сценариев) для проверки guardrails:

**Безопасный код проходит:**

    code = "import pandas as pd\nprint('Hello')"
    ok, msg = validate_code(code)
    assert ok
    output, files = run_code_sandbox(code)
    assert "Hello" in output

**Запрещённый импорт блокируется:**

    code = "import pandas as pd\nprint('Hello')"
    ok, msg = validate_code(code)
    assert ok
    output, files = run_code_sandbox(code)
    assert "Hello" in output

**Вредоносная команда не выполняется:**

    code = "import os\nprint('hi')"
    ok, msg = validate_code(code)
    assert not ok
    assert "запрещён" in msg.lower()

Проверяем, что наш валидатор выловит `__import__('os')`. (Если бы не, то subprocess всё равно выполнял бы, но в sandbox `os.system` может и сработать, хоть и echo – безвреден, но принципиально).

**Таймаут работает:**

    code = "while True:\n    pass"
    output, files = run_code_sandbox(code)
    assert "превысило" in output

Здесь бесконечный цикл, должны получить сообщение о таймауте.

**Ограничение доступа к сети:**

    code = "import socket\nsocket.socket().connect(('example.com', 80))"
    ok, msg = validate_code(code)
    assert not ok or run_code_sandbox(code)[0].find("Ошибка") != -1

Либо валидатор не пропустит `import socket`, либо, если пропустил, sandbox без сети не даст подключиться и вернёт ошибку.

Эти тесты дают уверенность, что guardrails на месте. Конечно, мы не охватим всех атак, но базовые проверки есть.

**Выводы по уроку 5.3:** Мы значительно укрепили нашего агента. Теперь даже если модель поведёт себя неверно или злоумышленник попытается через пользовательский ввод заставить её выполнить что-то опасное, у нас есть **многоуровневая защита**:

- Модель ограничена инструкциями (system-промпт не позволяет выходить за роль).

- Автоматическая валидация отсеет очевидно опасные команды.

- Песочница изолирует выполнение, чтобы даже прошедший код не навредил окружению.

- При любом сбое у нас предусмотрена обработка ошибок (модель может извиниться или мы покажем “не могу выполнить”).

Эти подходы соответствуют промышленным практикам: как и при разработке веб-приложений с небезопасным вводом, мы должны проверять и фильтровать то, что делает LLM. Интересно отметить, что Google в своём агентном SDK предлагает схожие механизмы policy enforcement и callbacks, а исследовательские работы предлагают архитектурные паттерны (Action-Selector, Plan-then-Execute, Code-then-Execute) для безопасных агентов. Мы уже фактически применяем *Code-Then-Execute* (генерация кода, потом sandbox) – он признан эффективным, если выполнять с хорошей изоляцией.

После всех этих сложных шагов технической безопасности, мы готовы к финальному аккорду модуля 5.
