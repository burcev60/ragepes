**Шаг 3: Изоляция исполнения (песочница)**  
**Цель шага:** Настроить изолированное окружение для запуска модельного кода. Обеспечить, что даже если вредоносный код проскочит, он не сможет выйти за пределы “песочницы” и нанести ущерб системе или данным.

Мы уже частично внедрили песочницу через проверки. Но настоящая изоляция – это на уровне ОС или интерпретатора:

- **Ограничение ресурсов:** запуск кода в отдельном процессе с пониженными привилегиями. Например, можно использовать Unix-подпроцесс с UID, у которого нет доступа ни к чему ценному. Или запуск в Docker-контейнере с только нужными пакетами. В Windows – можно попробовать AppContainer. В учебном проекте, вероятно, проще – можно использовать `multiprocessing` с отключением наследования дескрипторов.

- **Отключение интернета:** не подключать сетевые интерфейсы в контейнер (или отрезать через iptables). Так даже если код попытается что-то скачать – не выйдет.

- **Лимит по памяти и CPU:** например, использовать cgroup или ulimit – чтобы код не мог съесть всю память или нагружать CPU бесконечно.

- **Таймаут по времени:** если код не завершился за X секунд, убиваем процесс. Это защитит от зацикливания или зависания.

- **Изоляция файловой системы:** монтируем пустой временный каталог как рабочий. Положим туда только те файлы, которые нужны (CSV, etc.). Всё, вне этой папки для процесса ничего нет. В Python можно задать `cwd` для subprocess и не давать пути выше.

- **Переопределение опасных функций:** если мы не в контейнере, можно в коде подменить builtins (например, assign `builtins.open = restricted_open` перед exec). Но это ненадёжно на 100%, лучше реальная OS-изоляция.

В нашем примере, возможно, достаточно запустить код через `exec` в контролируемом dict. Но это слабая защита, т.к. модель может обойти (напр., `import builtins; builtins.open(...))`. Поэтому лучше subprocess.

Рассмотрим простой способ: модуль `subprocess`:

    import subprocess, shlex
    def run_code_sandbox(code: str) -> (str, list):
        # Сохраняем код во временный файл
        with open("sandbox/code.py", "w") as f:
            f.write(code)
        # Запускаем в отдельном процессе Python
        # - Посредством командной строки, с timeout
        try:
            result = subprocess.run(
                ["python", "code.py"],
                cwd="sandbox",  # рабочая директория с ограниченным набором файлов
                capture_output=True,
                text=True,
                timeout=5  # сек
            )
        except subprocess.TimeoutExpired:
            return "Ошибка: время исполнения превысило 5 секунд.", []
        output_text = result.stdout
        error_text = result.stderr
        # Собираем имена файлов, созданных в процессе (например, *.png)
        files = []
        for fname in os.listdir("sandbox"):
            if fname.endswith(".png") or fname.endswith(".csv") or fname.endswith(".txt"):
                if fname != "code.py":
                    files.append(os.path.join("sandbox", fname))
        if result.returncode != 0:
            output_text += f"\nОшибка выполнения: {error_text}"
        return output_text, files

Это упрощённый пример. Здесь:

- Код записывается в `sandbox/code.py`.

- `cwd="sandbox"` – мы предполагаем, что папка `sandbox` существует и там лежит, например, нужный CSV (`sales.csv`). Больше ничего нет.

- `capture_output=True` собирает stdout и stderr.

- `timeout=5` ограничит время. Можно также ограничить использование CPU (в Linux `subprocess` сам не даст, но можно, например, ulimit через `preexec_fn`).

- После выполнения собираем все .png файлы (на случай графики).

- Если был `returncode != 0`, мы приклеиваем stderr к output, чтобы модель знала, что пошло не так.

Такая песочница работает, хотя не идеальна (в теории, код мог например, создавать подпроцесс, но `subprocess.run` по умолчанию не разрешит вложенную?). В реальном мире можно использовать Docker: создать контейнер, запустить там python, подмонтировав CSV как read-only, и убить через timeout. Это надежнее, но требует Docker и больше настроек.

Ещё более хитрый метод – **RestrictedPython** (есть такая библиотека), она выполняет код внутри ограниченной среды на уровне питона. Но её ограничения могут помешать pandas. Поэтому контейнерный подход – более универсальный.

Важно: даже с песочницей, мы должны быть готовы к обходам. Исследователи активно выявляют уязвимости, и появляются рекомендации проектировать агентов с принципом *наименьших привилегий и сегрегации*. Например, один из подходов – *Dual LLM pattern*: один LLM генерирует потенциально опасное, но не исполняет, другой (более привилегированный) только читает безопасный вывод. У нас фактически тоже разделение: GPT генерирует код (недоверенная часть), а «система» исполняет его в клетке и даёт обратно результат. Это уже снижает риск, т.к. модель не выполняет код напрямую, а лишь косвенно.
