**Шаг 2: Валидация tool-аргументов/скриптов**  
**Цель шага:** Научиться автоматически проверять запросы инструмента (в данном случае – сгенерированный код или параметры функций) на соответствие политикам. Реализовать функцию валидации, которая перед выполнением кода сообщает, можно ли его исполнять или он нарушает правила.

Теперь, когда политики определены, их нужно применять. В нашем агенте самая сложная проверка – это проверка Python-кода строки. Мы можем использовать несколько подходов:

- Простейший: поиск запрещённых подстрок. Например, если в коде встречается `import os` или `os.system`, сразу блокируем. Так же с другими.

- Более надёжный: разбор AST (Abstract Syntax Tree) кода и анализ нод. В Python есть модуль `ast` – можно сделать `ast.parse(code)` и пройтись по узлам. Например, если встречается `ast.Import` с модулем вне `ALLOWED_MODULES`, или `ast.Call` какого-то запрещённого, или обращение к атрибутам вроде `os.system` – бросаем ошибку. Это требует чуть больше кода, но даёт уверенность, что даже если злоумышленник хитро замаскирует (например, `__import__("os")`), мы это отловим.

- Валидация аргументов инструментов: у нас пока инструмент – это код. Но аналогично, если бы был инструмент “Поиск в интернете”, можно проверять, не ищет ли он запрещённые вещи. Здесь уместно упомянуть, что **callbacks** или middleware для инструментов – хороший паттерн. Например, Google ADK (Agent Development Kit) предлагает *before_tool_callback* для проверки параметров перед выполнением. Мы по сути делаем такое же: *before_code_exec*, где проверяем код.

Напишем упрощённо функцию `validate_code(code: str) -> bool`:

    def validate_code(code: str) -> (bool, str):
        # Запрещённые ключевые слова:
        forbidden = ["import os", "import sys", "import subprocess", "import shlex",
                     "socket.", "requests.", "__import__", "open(", "eval(", "exec("]
        for pattern in forbidden:
            if pattern in code:
                return False, f"Запрещённый вызов: {pattern}"
        # Также ограничим длину кода:
        if code.count("\n") > 50:
            return False, "Слишком большой сгенерированный скрипт."
        return True, ""

Это примитивный пример. Он ловит самые грубые нарушения. Более изящно было бы использовать AST:

    import ast
    def validate_code_ast(code: str) -> (bool, str):
        try:
            tree = ast.parse(code)
        except SyntaxError as e:
            return False, f"Syntax error: {e}"
        for node in ast.walk(tree):
            # Запрет прямых импортов запрещённых модулей
            if isinstance(node, ast.Import):
                for alias in node.names:
                    if alias.name.split('.')[0] not in ALLOWED_MODULES:
                        return False, f"Импорт модуля {alias.name} запрещён."
            if isinstance(node, ast.ImportFrom):
                if node.module and node.module.split('.')[0] not in ALLOWED_MODULES:
                    return False, f"Импорт из модуля {node.module} запрещён."
            # Запрет вызова определённых функций
            if isinstance(node, ast.Call):
                # например, запрет open()
                if isinstance(node.func, ast.Name) and node.func.id == 'open':
                    return False, "Вызов open() запрещён."
            # ... другие проверки ...
        return True, ""

Конечно, это упрощённо – на практике список проверок больше. Но идея: **ни одна строка кода не исполнится, пока не пройдет проверку**.

Если проверка не прошла, как реагировать? Можно:

- Сообщить об ошибке пользователю: “Извините, запрос не может быть выполнен” – но это не очень дружелюбно.

- Лучше – сообщить *самой модели* и дать ей шанс исправиться. То есть, мы можем взять сообщение об ошибке и сделать дополнительный цикл с моделью: отправить ей что не понравилось, чтобы она переписала код без этого. Например:

  - Наш validator вернул `False, "Импорт модуля os запрещён."`

  - Тогда мы вызываем модель снова: *«Твой код не прошёл проверку безопасности: Импорт модуля os запрещён. Исправь код, убери небезопасные вызовы.»*

  - Модель GPT-4 должна понять и убрать/заменить проблему. Это своего рода **self-healing** попытка. Есть работы по этому поводу (например, ToolEmu, где LLM сам симулирует, что код сделает, чтобы проверить)[arxiv.org](https://arxiv.org/html/2503.18666v2#:~:text=Customizable%20Runtime%20Enforcement%20for%20Safe,an%20LLM%20sandbox%20before%20execution), но мы не углубляемся – достаточно простого цикла.

- Если после нескольких попыток (say, 2-3) модель не справилась – тогда уж отказ.

Помимо кода, **валидации требуют и другие инструменты**. Скажем, если агент выдает запрос веб-поиску, можно фильтровать неподобающие поисковые запросы (например, отсеять запросы, которые могут нарушать правила – о взломе, пиратстве и т.п., если политика компании этого не допускает). Также валидируем функции: если модель зовёт функцию `send_email(to, body)` – мы проверим, чтобы `to` был нашим доменом, например (чтоб не спамил вовне). Эти меры – общая концепция guardrails.
